# dagu Windows GPU：模式合成修复方案（2026-11-06）

这份文档是动手改代码前的设计蓝图。它回答一件事：qcdx 适配器初始化卡在 `0xC0000001`，要越过去必须合成什么、注入在哪、用什么值。实测数据来自 `bootgen=12` 冷启动（LOG2 回放，`aflt=0`/`mflt=0`/`dflt=0`，三组读取都没异常，是失败点真值）。

---

## 1. 失败链（已完全逆向，全镜像静态 + 运行时三值交叉确认）

```
FUN_1402934b0 (StartDevice 适配器初始化, RVA 0x2934b0)
  0x294460  ldr x8,[x20,#0x638]        ; a638 = framebuffer 描述符指针（实测非空）
  0x294464  cbz x8 → 0x294630          ; 非空，不走这条
  0x294468  ldr x14,[x8,#0x1118]       ; d1118 stride   实测 0
  0x29446c  ldr x15,[x8,#0x1108]       ; d1108 fb 基址  实测 0
  0x294470  ldr x13,[x8,#0x1110]       ; d1110 扫描大小 实测 0
  ... 把这三个零透传进 adapter+0x4268 区和 param 子结构 ...
  0x2944e8  bl  FUN_140276fd0(&param)  ; param[0]=adapter
       │
       ├─ FUN_140276fd0 (RVA 0x276fd0)
       │    0x277040  ldr w10,[x22,#0x780]   ; x22=[param[0]]=adapter, 读模式类型 实测 0
       │    0x277070  cmp w10,#5             ; 模式类型==5？ 实测否
       │    0x27708c  b.eq → 正常；否则 0x277090 存 0 到 sp+0x3c 继续（非致命）
       │    0x2771a8  bl FUN_140319498(&param2)
       │         │
       │         ├─ FUN_140319498 (RVA 0x319498)
       │         │    0x3194c0  第一块：param2[0]/[0x88]/[0x90] 任一空 → 返回 1
       │         │    0x319510  ldr x20,[x21,#0x98]; cbz → 0x319654  ; 第二块 15 指针

       │         │         └─ FUN_140319718 (RVA 0x319718)
       │         │              0x3197a8 ldr w8,[x1,#8]; sub #5; cmp #1; b.hi 跳过
       │         │                       ; 模式类型∈{5,6} 时检查下面三项：
       │         │              0x3197bc [obj+0xa8] >= 0x5000   ; ★硬门 2a：扫描大小，源自 d1110
       │         │              0x3197c4 [obj+0xa0] != 0        ; ★硬门 2b
       │         │              0x3197cc [obj+0x98] != 0        ; ★硬门 2c
       │         │              任一不满足 → w21=4（失败）
       │         └─ 返回 2 → FUN_140276fd0 把 w22 置 0x80004005
       └─ cbnz w0 → 0x29473c: mov w19,#0xC0000001 → 失败尾 0x2947ac
```

**结论：不是只差 `+0x780` 一个字段。** framebuffer 描述符 `a638` 非空，但它指向的内容 `d1108/d1110/d1118`（fb 基址 / 扫描大小 / stride）全是 0；模式类型 `+0x780` 及其几何兄弟字段也没被枚举填。整个模式块是空壳。根因：`map=0`、垫片顶替 SMMU、无真实 DPU/DSI 链路，上游模式枚举（`FUN_140260850`）把显示头标成有效（`+0x630=1`）却没产出模式数据。

## 2. 实测真值（bootgen=12，失败点，LOG2）

| 字段 | 偏移 | 实测 | 需要 |
|---|---|---|---|
| 显示头使能 | adapter+0x630 | 1 | 1（已满足） |
| fb 描述符指针 | adapter+0x638 | `0xFFFF808F_E34C7000` 非空 | 非空（已满足） |
| 模式类型 | adapter+0x780 | **0** | **5** |
| 模式标志 | adapter+0x784 | 0 | 待定 |
| sub-mode id | adapter+0x788 | **0** | `0x026a0064`/`0x02760014`/`0x02a80014`/`0x02b2000a` 四选一 |
| 几何 a/b | adapter+0x3b78/0x3b7c | 0 / 0 | 待定 |
| stride 位移 | adapter+0x3b90 | 0 | 待定 |
| 打包几何 | adapter+0x46c4 | `0x4010`（低 11 位=16） | 非关键（bfxil 取低 11 位进描述符） |
| fb 基址 | a638 描述符 +0x1108 | **0** | GOP 显存基址 |
| 扫描大小 | a638 描述符 +0x1110 | **0** | **≥0x5000** |
| fb stride | a638 描述符 +0x1118 | **0** | 非零 |

合法 sub-mode id 常量来自 `276fd0` literal pool `0x277284`–`0x277290`。

GOP 显存（`bootgen=9` 记到，UEFI 已点亮面板用的那块）：基址 `0x9C000000`、大小 `0xFA0000`（15.6 MiB）。这是复用候选。

**面板实测参数（2026-11-06，B 槽 Linux 读回，面板 `l81a_42_04_0a_dual_dphy_video`）：**
- 分辨率 **1600×2560**，32bpp（`/sys/class/drm/card0-DSI-1/modes` = `1600x2560`，`/sys/class/graphics/fb0` virtual=`1600,2560` stride=`6400` bpp=`32`）。
- stride = **6400 = 0x1900**（1600 × 4）。
- fb 大小 = 1600 × 2560 × 4 = **0xFA0000** —— 与 GOP 显存大小 `0xFA0000` 精确吻合，交叉确认 GOP 点亮的就是这块满分辨率 fb，基址 `0x9C000000`。

## 3. 要合成什么（三组，缺一不可）

### A. 模式类型组（adapter 头 0 块，步长 0x6a8，头 0 在 adapter+0..0x6a8）
- `+0x780 = 5`（硬门 1）
- `+0x788 = 0x026a0064`（合法 sub-mode id，避开错误日志；非致命门）
- `+0x784`、`+0x3b78`、`+0x3b7c`、`+0x3b90`：非硬门，填 0 或面板几何均可越过启动门；为自洽建议填 1600/2560 相关值

### B. framebuffer 描述符内容（a638 指向的描述符）
- `+0x1108 = 0x9C000000`（GOP fb 基址）
- `+0x1110 = 0xFA0000`（扫描大小 15.6 MiB，远超 0x5000 门槛）
- `+0x1118 = 0x1900`（stride = 1600×4 = 6400）

### C. 第一块对象（319498 第一块，需 param2[0]/[0x88]/[0x90] 非空）
- 这三个由 `276fd0` 在 `0x27713c`–`0x277190` 从 param 子结构填；param 子结构由 `2934b0` 从 adapter+0x4268 区建。只要 A/B 两组填对，这块会自然建成（两个 thunk 指针 `0x2772b0`/`0x2772d0` 是现成的）。

## 4. 注入点（关键决策）

现 shim 钩子在失败尾跳板 `0x2c777c`，是读完 `+0x780`、判完失败**之后**才跑，写晚了。必须换更早的点。

**候选注入点：`FUN_1402934b0` 内 `0x294460` 之前**（x20=adapter live，a638 已可读）。在这里插跳板调 shim：
1. 填 A 组（adapter+0x780 组）
2. 填 B 组（a638 描述符内容）
3. 返回后让 2934b0 重新读 a638 描述符（此时 d11xx 已非零），一路透传正确值给 276fd0/319498/319718，三道门全过。

注入方式沿用现有 loadpatch 机制（qcdx 独立副本 `dagu-qcdx/qcdxkm8250.sys` 已在用，shim 运行时按 RVA 打补丁）。新增一个跳板 site，在 shim 的 `PatchQcdx` 里按 RVA 写入 `bl` 到新的 naked thunk，thunk 保存 x20、调 `FillMode(adapter)`。

## 5. 面板实测参数（2026-11-06，B 槽 Linux 读实）

从设备 Linux 侧读实（DRM/fb/驱动三处一致）：

- 面板 `l81a_42_04_0a_dual_dphy_video`，HX83121 控制器
- **分辨率 1600×2560，32bpp**（`/sys/class/drm/card0-DSI-1/modes`、`/sys/class/graphics/fb0/*`、`himax-dagu ... HX83121 1600x2560`）
- **stride = 6400 = 0x1900**（1600×4）
- **fb 大小 = 1600×2560×4 = 0xFA0000**，与 `bootgen=9` 记到的 GOP 显存大小 `0xFA0000` 完全吻合，GOP 基址 `0x9C000000`

**几何字段用法（`276fd0` 反推，关键简化）：** `+0x784/+0x3b78/+0x3b7c/+0x3b90` 在 `276fd0` 里只是被拷进模式描述符（`0x277030`–`0x277088` 一组 `ldr`/`stp`），**本身没有硬校验门**。`+0x3b90` 经 `mvn w9,w8,lsl #14` 参与 stride 标志位计算，但不卡启动。`+0x788`（sub-mode id）匹配四常量之一只为选对像素格式分支、避开错误日志（`0x2770d8`，非致命，匹配不上也继续）。

**真正的硬门只有两个**：`+0x780==5`（`0x319660`）和描述符扫描大小 `[desc+0x1110]≥0x5000`（`0x3197bc`，仅当模式类型∈{5,6} 时检查）。

## 6. 待验证风险

**GOP fb 能否直接复用**：qcdx 把扫描输出指向 GOP 已点亮的 fb，最贴近"有背光无帧"现状。但 qcdx 后续可能对 fb 做自己的页表映射（map=0 下无真实映射），需验证写进描述符的物理地址 qcdx 会不会再翻译。这是过了三道门之后的下一个可能卡点，无法纯静态排除，只能下一次冷启动实测。
