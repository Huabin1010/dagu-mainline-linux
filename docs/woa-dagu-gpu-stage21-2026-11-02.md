# dagu Windows GPU：阶段 21（问题码 43 是 SMMU 接口第 25 槽返回空）

阶段 20 把 `qcdx` 等待的设备接口和槽位布局逆出来，垫片按这个约定回答了查询。本阶段把 SMMU 回调成功之后、适配器被报成问题码 43 的那一步钉到接口第 25 槽，并按父区间的真实约定改了垫片。原版 `qcsmmu8250` 仍然不加载，`map` 仍然是 0，不写 APPS SMMU `0x15000000`。

驱动是 `winarm/drivers/QC8250/Drivers/Graphics/DXKM/qcdxkm8250.sys`，首选映像基址 `0x140000000`。下面的地址都是 RVA。

## 1. 上板读数

诊断映像在 `0x267820` 的失败返回处把调用者地址编进返回值（符号位保持置位，调用者仍走失败路径）。2026-11-02 19:12 那次拉起读到：

| 项 | 值 |
|---|---|
| `fail` | `0xC00440EC` |
| 解码 | 低 28 位 `0x440EC`，加上页 `0x267000`，返回地址 RVA `0x2AB0EC` |
| 对应调用 | `0x2AB0E8` 的 `blr`，下一条就是 `mov w19, w0` |
| `step` | `0x61` |
| `ncall` | 48（垫片每 16 次槽调用才刷一次） |
| `seen0` / `seen1` | `0x18400044` / `0x9080`，槽 2、6、22、27、28、39、44、47 |
| 设备 | `ACPI\QCOM253A\0`，问题码 43（`CM_PROB_FAILED_POST_START`） |

这次捕获只替换了 `0x267820` 里「回调返回空指针」那条路径。参数检查失败走的是另一条，返回 `0xC000000D`，不会编出 `0xC00440EC`。所以这次读数表示：参数和区间检查都过了，被调用的函数返回了空指针，`0x267820` 把它变成 `0xC0000017`。

同一条状态一路原样传回去：`0x2AB0EC` 写入 `w19`，`0x2AB1B4` 返回，`0x29BC6C` 写入 `w19`，`0x29C7A8` 返回，`0x2941B8` 写入 `w19`。负数进入 `0x2947AC`。适配器初始化失败，PnP 记问题码 43。

诊断映像还做了两件和本失败无关的事：跳过失败收尾（收尾会在空表上崩），以及给其余 `0xC0000017` 常量打了不同的标记。它不是修复。

## 2. 调用链

适配器初始化 `0x2941B4` 调用 `0x29BA78`。`0x29BC50` 看到适配器 `+0x4C8` 的长度不是 0，就调用 `0x2AAFF0`：

| 参数 | 来源 |
|---|---|
| 区间对象 | 适配器 `+0x41D8` |
| 长度 | 适配器 `+0x4C8`，非 0 |
| 偏移 | 适配器 `+0x4C0` |
| 输出 | 适配器 `+0x4D8` |
| 标志字 | `0x1E` |

`0x2AAFF0` 先分一块 0x40 字节的描述符，再在 `0x2AB0E8` 做虚调用。虚函数是 `0x267820`，所在虚表是 `0x14BFE8` 的 `+0x78`。`this` 不是区间对象本身，而是 `[[区间对象]+8]`。

`0x267820` 确认：

- `this+0xD0` 不是空。
- 区间对象本身、它的首字段、标志指针、输出描述符都不是空，长度不是 0。
- 区间对象 `+8` 的类型是 1。否则返回 `0xC000000D`。
- 偏移落在 `[区间+0x10, 区间+0x10 + 区间+0x18)` 里，长度先按页对齐 `(size + 0xFFF) & ~0xFFF`。装不下也返回 `0xC000000D`。

这些检查都过了，才调用 `[[this+0xD0]+0xE8]`。返回空就记日志并返回 `0xC0000017`。返回非空时，描述符写成：`+0` 为 1，`+8` 为偏移，`+0x10` 为按页对齐的长度，`+0x28` 为区间对象，`+0x30` 为这个指针，并给区间对象 `+0x30` 做一次原子加一。`0x2AAFF0` 成功后把这块描述符的指针存进调用者给出的输出（适配器 `+0x4D8`）。

## 3. `this+0xD0` 是接口副本，`+0xE8` 是第 25 槽

虚表 `0x14BFE8` 的对象由 `0x2654E0` 构造。构造函数把 `+0xD0` 先清成空，向设备接口查询 0x1A0 字节、版本 2。查询类型是 `{C178BD17-15DC-4145-A907-61327EC6284D}`。返回的 `INTERFACE.Size <= 0x1A0` 时，用池标签 `qDX6` 再分 0x1A0 字节，把整份接口拷进去，指针放在对象 `+0xD0`。`Size > 0x1A0` 才改用另一份 GUID、长度 `0x198` 重查；那条路径要求 `Size <= 0x198`，否则对象留着、`+0xD0` 仍是空。

垫片把 `Size` 设成对方请求的长度，所以走的是第一条：`+0xD0` 是一份 0x1A0 的接口副本。

ARM64 上接口头 0x20 字节之后才是槽。偏移 `0xE8` 的槽号是 `(0xE8 - 0x20) / 8 = 25`。`0x267820` 调用的就是这份副本里的第 25 槽。映像里还有别的 `+0xE8` 间接调用，上板返回地址 `0x2AB0EC` 对上的是这一处。

调用约定：

```
指针 = 槽25(区间对象+0x28, 按页对齐的长度, 偏移, 0x160)
```

`0x160` 是标志字 `0x1E` 进 `0x267820` 之后重新打包的结果：bit1 变成 `0x20`，bit2 变成 `0x40`，bit4 变成 `0x100`。返回值必须是非空指针。空指针就是这次的 `0xC0000017`。

同一个接口副本上，虚表 `+0x48`（`0x2670D0`）会调用偏移 `0xA8`，也就是第 17 槽，用来放开一批已经记下的指针。第 25 槽负责交出指针，第 17 槽是同一份接口上的释放入口。

## 4. 第 25 槽前面的父区间

`0x267820` 拿到的区间对象不是第 25 槽自己建的。适配器初始化在调用 `0x2AAFF0` 之前，先由 `0x29B168` 按 16 字节池名匹配出父区间，再交给 `0x2AAC10`。这次失败的区间是适配器 `+0x41D8`，名字是 `MdpNonSecurePT`。`0x2AAC10` 分 0x38 字节（池标签 `qDXD`），然后调用虚表 `+0x60`，也就是 `0x2672D0`。

`0x2672D0` 对同一份接口副本连续做三次调用。`0x2672D0` 到 `0x267450` 的反汇编是：

| 槽 | 接口偏移 | 调用 | 成功条件 |
|---|---|---|---|
| 22 | `+0xD0` | `句柄 = 槽22(*(父对象+0x50), 长度, 标志)` | 返回非空。空则失败，区间建不出来 |
| 28 | `+0x100` | `长度 = 槽28(句柄)` | 64 位返回值非 0，写入区间 `+0x18`。返回 0 时状态是 `0xC0000001` |
| 27 | `+0xF8` | `基址 = 槽27(句柄)` | 返回值恰好是 1 时失败，状态同样是 `0xC0000001`。0 和其他值都接受，写入区间 `+0x10` |

成功时区间对象是：`+8` 类型 1，`+0x10` 基址，`+0x18` 长度，`+0x28` 第 22 槽的句柄。第 25 槽的第一个参数就是这个句柄。`0x267958` 起的四条指令是 `ldr x0, [x21, #0x28]`、`mov w3, w24`、`mov x2, x23`、`mov x1, x25`，然后 `blr` 第 25 槽。

旧垫片能走到第 25 槽，是因为这三槽碰巧满足了检查，语义是错的。第 22 槽交回一块清零页，所以非空。第 28 槽回显内核地址，被当成区间长度，大得能装下任何 32 位偏移。第 27 槽返回 0，避开了「返回 1 就失败」。

`0x29EB80` 在进 `0x29BA78` 之前解析固件变量 `UEFIDisplayInfo`，把按页对齐的像素缓冲大小写到适配器 `+0x4C8`，把 `+0x4F0` 拷到 `+0x4C0` 当作偏移。大于等于 4GB 的地址会被丢掉，所以子分配偏移是一个 32 位 GPU 地址。第 25 槽被调用之前，`0x267820` 先检查这个偏移落在 `[基址, 基址+长度)` 里。

## 5. 描述符交出去之后

`0x267820` 把第 25 槽的指针放进描述符 `+0x30`。紧接着的使用者是 `0x29BD18` 调用的 `0x2AB5D8`：它按页做索引表（池标签 `qDXB`），表项是 GPU 虚拟地址的页号，不是物理页帧，然后调用 `0x2AB318`。

`0x2AB318` 走虚表 `+0x98`（`0x267F70`）。`0x267F70` 要求描述符 `+0x30` 非空，再调用接口 `+0x90`，也就是第 14 槽：

```
状态 = 槽14(第25槽返回的指针, 页表)
```

返回负值才失败。0 是 `STATUS_SUCCESS`。页数小于按页对齐长度时，描述符 `+0x38` 的 bit0 置位，还会再调接口 `+0x108`（第 29 槽）。这两槽原来就返回 0。

## 6. 垫片按这个约定交回对象

[`dagu-smmushim.c`](../port/dagu/windows-drivers/dagu-smmushim/dagu-smmushim.c) 里第 22、25、27、28 槽现在共用一块带魔数的非分页对象，不再把内核地址当成区间长度：

- 第 22 槽记下窗口。调用方传入的字节长度小于 4GB 时，窗口抬到 4GB、基址保持 0。`0x29B0E0` 只保存区间指针和名字，垫片并不按这个长度去分配内存。抬高窗口只为了让 `0x9C000000` 这种 32 位 GPU 地址通过 `0x267820` 的边界检查。
- 第 28 槽返回窗口的字节长度，不是指针。4GB 的低 32 位是 0，注册表里的 `retlo` 因此显示 0；`0x2672D0` 比较的是完整的 64 位 `x0`。
- 第 27 槽返回基址 0，绝不返回 1。
- 第 25 槽在长度非 0 时返回子区间对象，并把偏移、长度、是否成功写进 `suboff`、`subsz`、`subok`。
- 第 6 槽仍是原来的清零页。第 14、29 槽仍返回 0。`map` 仍是 0，第 47 槽不会去写 `0x03DA0000`。
