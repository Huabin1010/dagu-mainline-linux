# 前置像素通路只出一帧：怎么查到根因、怎么修的

记录日期：2026-10-24。修复内核 `#626`，提交 `c8cd60b`。  
设备：小米平板 5 Pro 12.4（dagu），Linux 板序列号 `ab22268c`，只用 B 槽。安卓对照板 `53dcc70`，只读。

## 1. 现象

前置 imx596 走图像前端 1 的像素通路，输出线性 NV12 2320×1320，步长 4096。从 `#412` 到 `#624`，每次测试最多只出一帧（8110080 字节）：

- 第二帧帧起始后不到 1 毫秒管线就停了，驱动还没来得及做任何动作。
- 相机接口调试字 1（`0x27f0`）停在 `0x10218000` 或 `0x10218010`。
- 没有违例、溢出或总线错误中断。传感器接口中断照常增加，图像前端中断停住。

之前的改法都不对：改注册更新的时机、重装写主、改写主丢帧图案、照抄安卓的缩小通路、整幅直通、重放安卓的命令包、改伽马和白平衡表、改帧尺寸和相位。这些都是按"某个寄存器值不对"去猜，一次刷一个值。

## 2. 换方法：先看清是哪个模块停住

### 2.1 一组以前没读全的调试字

高通内核 `cam_vfe480.h` 定义了 14 个顶层调试字：`0x80 0x84 0x88 0x8c`，然后是 `0x9c` 到 `0xc0`，中间跳过了 `0x90`–`0x98`。`0xdc=1` 打开。驱动以前只在溢出中断里读前 4 个，这次停机没有溢出，所以这组字一直没人看过。

每个字是 8 个 4 位字段，每个字段对应一个相机逻辑核模块。480 的模块名表没有公开。位义是从 Linux 第一帧的变化轨迹反推出来的：

| 值 | 什么时候出现 | 含义 |
|---|---|---|
| `5` | 帧间；没用到的模块；安卓采样里全是 5 | 空闲 + 就绪 |
| `1` / `3` | 第一帧数据流动时来回跳 | 帧内：就绪 / 就绪 + 有效 |
| `2` | 只在第二帧停机时出现 | 有效但不就绪：手里有数据，交不出去 |

位 0 是就绪，位 1 是有效，位 2 是空闲。

### 2.2 第一次采样（用户态，不刷机）

- Linux 停机时用 `/dev/mem` 只读：`0xa0`–`0xac` 有 16 个位置是 `2`，下游 `0xb0`–`0xbc` 全是 `1`。说明是中间被堵住了，不是没开工。
- 安卓预览时用手写的只读内核模块（`tools/dagu-ife-magisk/dagu_ife_top.S`）采了 96 次，所有位置都是 `5`。
- 两边全窗 `0x0`–`0xd000` 各读一遍，有 440 个字不同。

用户态轮询有风险：后置测试 3 帧跑完、时钟已经关了，轮询还在读，Linux 板总线卡死重启。所以第二步把采样搬进了驱动。

### 2.3 一次刷机装好仪器（`#625`）

| 工具 | 参数 | 作用 |
|---|---|---|
| 飞行记录器 | `dagu_fr_us`（默认 20 微秒）、`dagu_fr_ms` | 从相机接口启动开始，用硬中断定时器读 23 个字：两个相机接口调试字、14 个顶层调试字、中断状态、写主 4/5 调试和地址状态。只记变化，最多 2048 条。在 `vfe_wm_stop()` 里停，这时时钟还开着。停流时打印 `dagu fr` 行 |
| 运行时覆盖表 | `dagu_ovr` | 格式 `时机:偏移=值,...`，时机有 `init`（程序写完、第一次注册更新之前）、`go`、`sof`、`eof`。只允许写 `0x2c` 和 `0x2000`–`0x9ffc` |

装好以后，每个假设就是 15 秒的运行时试验，不用再刷机：

```text
echo 2000 > /sys/module/qcom_camss/parameters/dagu_fr_ms
echo -n 'init:0x4460=0,init:0x4660=0' > /sys/module/qcom_camss/parameters/dagu_ovr
DAGU_IFE_PIX=front ./scripts/dagu-ife-pix-test.sh
dmesg | grep 'dagu fr'
```

## 3. 记录器看到的

### 3.1 第一帧的时间轴（`#625`，默认配置）

时间从第一帧帧起始算。行时间约 5.3 微秒（帧长 `0x189e` 行，30 帧）。

| 时刻 | 事件 |
|---|---|
| 0 | 帧起始 |
| 5.16 毫秒 | 纪元中断（第 487 个行对） |
| 7.08 毫秒 | 写主 4、5 写满，地址状态翻转，约第 1336 条输入行 |
| 10.3 毫秒 | 帧结束，共 1952 行 |

写主在第 1336 行左右就写满了，说明竖直方向是 1:1，输出是画面上面的 1320 行。这件事和停机无关，留在第 7 节。

### 3.2 帧间隔里有两个模块不空闲

| 运行 | 帧结束后、第二帧之前的 `0xa0` |
|---|---|
| `#625` 默认 | `0x55515155`，整段约 23 毫秒都是这样 |
| 安卓 | `0x55555555` |

其他所有位置在帧结束后都回到 `5`，只有 `0xa0` 的第 2、4 个字段一直是 `1`：就绪，但没回到空闲。它们没能结束第一帧。

第二帧帧起始后约 40 微秒，这两个字段先变成 `2`；再过约 160 微秒，`0xa0`–`0xac` 一共 16 个位置变成 `2`，相机接口停住。

## 4. 逐项排除（全部走运行时覆盖）

| 改动 | 帧数 | 帧间隔 `0xa0` |
|---|---|---|
| 不改 | 1 | `0x55515155` |
| 裁剪、缩放器的帧尺寸字 `+0x68` 都改成 `0x0a1f079f`（2592×1952） | 1 | 同上 |
| 再把裁剪、缩放器的竖直字段全部清 0 | 1 | 同上 |
| 关掉显示缩放器 `0x4c60/0x4e60` | 1 | 同上 |
| 关掉后钳位 `0x5060/0x5260` | 0（尾段先堵） | 同上 |
| 关掉 `0x5860/0x5a60` 钳位 | 1 | 同上 |
| 关掉预钳位 `0x4260` | 1 | 同上 |
| **关掉 `0x4460/0x4660`** | **3** | `0x55555555` |
| **关掉 `0x4860/0x4a60`** | **3** | `0x55555555` |
| 四个全关，连续 90 帧 | **90** | `0x55555555` |

只有关掉 `0x4400/0x4600` 或 `0x4800/0x4a00`，第一帧才能正常结束，第二帧才能接着走。

## 5. 根因

驱动把 `0x4400/0x4600` 当成显示通路的"裁剪"（`CLC_CROP`/`CLC_CROP_C`），把 `0x4800/0x4a00` 当成"中间钳位"（`CLC_RNDCLAMP_MID_Y/C`）。实际上它们是**人脸检测支路**：亮度/色度缩放器加亮度/色度圆整钳位，输出到总线写主 8/9。

依据：

- CAF（Code Aurora Forum，高通开源代码库）`cam_vfe480.h` 的输出口表里，`VFE_OUT_FD` 对应写主 8、9，名字是 `FD_Y`/`FD_C`，最大 1920×1080，按行写。
- 安卓相机 1 的读回能对上 640×480 的人脸检测图：
  - `0x446c=0xc081999a`：Q21 定点 4.05，等于 2592/640。
  - `0x4474=0xc0822222`：4.067，等于 1952/480。
  - 色度 `0x466c=0xc1033334` 是 8.1，等于 2592/320。
  - 钳位 `0x4868/0x486c = 0x1df/0x27f`，即 480 行、640 列。
  - 写主 8 图像配置 0 是 `0x01e00280`（640×480），写主 9 是 `0x00f00280`（240×640）。

Linux 的问题是：

1. 打开了这条支路（`MODULE_CFG=1`）。
2. 填进去的是从别的会话抄来的显示尺寸（1472 行、2320×1320 钳位）。
3. 写主 8/9 一直关着。

结果这条支路的第一帧收不了尾。第二帧数据进来时，它和显示通路共用的上游被堵住，整条管线连同相机接口一起停下。没有任何模块报错，所以没有错误中断。

这就解释了为什么第一帧总能出、第二帧一开始就停，以及为什么改注册更新时机、写主、缩小通路都救不回来：堵点根本不在显示通路上。

## 6. 修复（`#626`）

- `camss-vfe-480.c`：
  - 新增 `vfe_480_fd_off()`，把四个块的 `MODULE_CFG` 写 0。像素程序在原来写裁剪和中间钳位的位置改为调用它。
  - 删掉所有往这四个块写值的代码：`vfe_480_crop()`、9 字打包、中间钳位使能、竖直字段的补写。前置和后置都改。
  - 在宏定义处注明这四个块是人脸检测支路。
- `apply-overlays.sh`：删掉 18 条要求保留旧裁剪写法的检查，换成一条：人脸检测支路必须关着，而且不准再打开。

`#626` 回归，不带任何覆盖：

| 项 | 结果 |
|---|---|
| 前置冷启动后第 1 次、热启动第 2、3 次 | 每次 3 帧，24330240 字节；调试字 1 是 `0x82d68008`（和安卓一样）；色度 127.3；帧间隔全是 `5` |
| 前置 90 帧 | 729907200 字节，违例号 0，没有溢出 |
| 后置 | 3 帧，9331200 字节，违例号 0 |

## 7. 还没解决的

- **视场是裁出来的，不是缩小的。** 竖直 1:1（写主在第 1336 行写满），水平缩放器相位 `0xc0200000` 也是 1:1。输出是传感器画面左上角的 2320×1320。
- **画质。** 亮度均值约 49；有成块的绿/品红色斑；顶上有一条紫线。这些属于图像处理参数，和停机无关。

两件都可以用记录器加覆盖表继续做，不需要每次刷机。

## 8. 经验

- **先找"谁停了"，再谈"哪个值不对"。** 顶层调试字能直接看到每个模块是否就绪、是否有效、是否空闲，一次采样就能把范围缩到一对模块。以前两百多次刷机都是在猜值。
- **模块名要从高通的输出口表和安卓读回里核实。** 寄存器偏移相同，不等于功能相同。这次被当成"显示裁剪"的块，其实是另一条输出支路。
- **没有写主接收的支路不要打开。** 高通用户态框架只在拓扑里有人脸检测口时才配这条支路，Linux 没有这个口。
- **用户态 `/dev/mem` 只在流确定开着时读。** 采样放在驱动里，在关时钟之前停。
