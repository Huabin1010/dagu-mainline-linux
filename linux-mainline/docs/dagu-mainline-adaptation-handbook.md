# dagu 主线 Linux 适配全记录与心得

记录日期：2026-10-24。对应内核 `#629`，仓库提交 `9b51b8c`。

设备：小米平板 5 Pro 12.4，内部代号 dagu。系统：主线 Linux 7.0 + Ubuntu 26.04 桌面。

这份文档把从 2026 年 7 月解锁到 10 月相机走上硬件通路的整个过程串起来：每个子系统是什么硬件、坏在哪、根因是什么、怎么修、修完量到了什么、还剩什么。最后一部分是心得。细节和每一刀的遥测仍在各专题文档里，本文给出路径，不重复抄数字表。

- HyperOS 2，`OS2.0.10.0.ULZCNXM`，安卓 14，内核 `4.19.157-perf`。

## 4. 启动链

细账：`linux-mainline/docs/dagu-fastboot-abl-ramdisk.md`、`dagu-dtbo-abl.md`、`elish-abl-legacy-boot-path.md`、`abl-vs-lk.md`、`devices/dagu-hyperos-os2/02-boot-chain.md`。

### 4.1 链路

```text
片内一级引导 → xbl → abl（UEFI 应用 LinuxLoader）→ 内核
```

引导程序做的事：

- 提供 fastboot（音量下 + 电源）。
- 读当前槽的 `boot`、`vendor_boot`、`dtbo`、`vbmeta`。
- 按 `qcom,msm-id` / `qcom,board-id` 选设备树，再按板号盖叠加层。
- 在显示控制器上画开机图。主线显示驱动起来之前屏幕不会重画，所以“开机图冻住”只说明引导程序跑过了。
- 跳内核时看门狗还开着；高通虚拟机监控程序占着异常等级 2。

`abl` 本体是加密或强压缩过的固件卷，不能反汇编。下面关于它内部流程的说法，都来自高通开源的 `QcomModulePkg` 祖先源码加真机实验。

### 4.2 原厂镜像格式

| 分区 | 格式 |
|---|---|
| `boot` | 安卓启动镜像头版本 3；内核是约 52 MiB 的原始 `Image`（不压缩、不是可执行映像格式），`text_offset=0x80000`；不含设备树 |
| `vendor_boot` | `VNDRBOOT` 版本 3；设备树是 4 份拼接：kona v2.1（`0x164 0x20001`，板号 `0 0`，引导程序选这份）、v2、v1，再加 173 字节垃圾 |
| `dtbo` | 魔数 `0xD7B7AB1E`，29 条；第 15 条 `model="xiaomi dagu"`，板号 `0x33 0`，约 494 KiB 高通专有引脚和电源片段 |
| `vbmeta` | 安卓验证启动；自造镜像必须 `flags=3`（关校验、关哈希树） |

活机设备树盖完叠加层后板号是 `0x33`，命令行带 `androidboot.dtbo_idx=15`。

### 4.3 引导程序收什么、拒什么

| 试过的做法 | 结果 |
|---|---|
| 从零 `mkbootimg` 打头版本 2/3 | 拒收或秒回 |
| `vendor_boot` 里放 4 份拼接设备树 | 载入错误，原厂内核也不跳 |
| 用活机 dump 出来、已经盖过第 15 条的设备树当 `vendor_boot` 设备树 | 原厂 4.19 内核也约 6 秒回兔子 |
| 合法但 0 条的叠加分区 | 约 6 秒回兔子 |
| 存根叠加分区第一版（主线设备树没带符号表） | 约 3 秒回兔子（盖不上） |
| 用 magiskboot 拆原厂 v3 再塞主线内核 + 单份设备树 + 29 条空操作存根叠加分区 | 能跳，这是现行做法 |
| elish 那种头版本 0 + `gzip(Image)` 尾附设备树 + 擦掉 `dtbo_b` | 09-09 验证能跳（`build-bootimg-legacy.sh`），留作备用 |

为什么空叠加分区不行：高通源码 `GetBoardDtb()` 在条目数为 0 时循环一次都不跑，返回空，于是当成载入错误。而擦掉的分区没有魔数，校验先失败，引导程序就走“内核尾附设备树”那条路，根本不进 `GetBoardDtb()`。“擦掉”和“合法的空表”对引导程序是两回事。

为什么 elish 的老格式能成：头版本小于 3 时引导程序不打开 `vendor_boot`，也就不会把安卓的厂商内存盘拼进来；内核是压缩包时，解压函数把压缩流消耗的长度写进 `DtbOffset`，后面紧跟的设备树正好被找到；叠加分区被擦掉，校验失败，走尾附设备树。三件缺一件就掉进严格的 v3 路径。

### 4.4 现行打包（`build-bootimg.sh`）

- 用 `magiskboot` 拆 `dumps/.../images/` 里原厂的 `boot_a.img` 和 `vendor_boot_a.img`，换内核、换内存盘、换设备树后再按原样打回，保留原厂的系统版本和补丁日期字段。
- 内核：
  - Linux 7.0 的 `Image` 头里 `text_offset=0`，入口在文件约 37 MiB 处，里面还嵌了一个空设备树（魔数 `d00dfeed`）。
  - 脚本把所有嵌入的 `d00dfeed` 抹成 0，免得引导程序把它当成设备树。
  - 默认在前面加一个 `0x80000` 的头，`code0` 跳过这段，头里写 `text_offset=0x80000`，和原厂一致。打包后会校验载荷正好是 `Image + 0x80000`。
  - 不要加 `nokaslr`：7.0 把 `0x80000` 的物理错位当成随机化的低位，引导程序加载到 `0xa0080000` 也能按 2 MB 块映射。
  - 备选：`BOOTIMG_STUB_PAD=1` 是早期的 2 MiB 跳板；`BOOTIMG_RAW=1` 原样塞。
- 内存盘：自造的 gzip cpio（`initramfs/init.c` + 一个极小的 shell + dropbear），不是 HyperOS 的。
- `vendor_boot`：只放一份主线设备树，用 `fdtput` 改成 `qcom,msm-id = <0x164 0x20001>`、`qcom,board-id = <0 0>`，和原厂第一份一致。去掉原命令行里的 `reboot=panic_warm`（不然内核一崩就瞬间回兔子，什么都看不见）。
- 设备树要带符号表：`apply-dts.sh` 写 `DTC_FLAGS_sm8250-xiaomi-dagu := -@`。
- 存根叠加分区 `out/dtbo-stub.img`：29 条空操作叠加层，逐条复制原厂板号，约 10.9 KiB。存根不能改根节点的 `compatible`：改成 kona-mtp 那次，高通带宽压缩配置查不到，显示控制器 `-EINVAL`。
- 打包前要 `unset BOOTIMG VBOOT`，环境里残留的路径会让脚本写到错误的地方。

### 4.5 命令行（`CMDLINE_EXTRA`）

| 参数 | 原因 |
|---|---|
| `clk_ignore_unused pd_ignore_unused regulator_ignore_unused` | 内核在启动后期会关掉“没人用”的时钟、电源域和电源轨，面板的电源轨一断，开机画面就没了 |
| `cpuidle.off=1` | 6 号核进了电源状态协调接口的掉电空闲态后再没回来，约 24 秒硬锁死。高通虚拟机监控程序要求先由下游驱动编好睡眠/唤醒集，那部分还没移植 |
| `arm-smmu.disable_bypass=0` | 系统内存管理单元在帧缓冲控制台接管 26 毫秒后复位所有流映射；监控程序把显示流交出来时是直通态，一个映射都没保留，默认策略会让显示控制器读开机画面时出错，表现为背光亮、画面黑 |
| `fw_devlink=off fw_devlink.sync_state=disabled` | 关掉设备链接的依赖等待 |
| `kpti=off` | 和活机命令行一致 |
| `msm.dpu_use_virtual_planes=1` | 显示处理单元用虚拟图层 |
| `console=ttyGS0,115200 console=tty0 fbcon=font:TER16x32` | 日志同时走串口小工具和屏幕；大字体在 1600×2560 上还能看 80 行 |
| `ignore_loglevel loglevel=8` | 打全日志。注意它会让中断线程里的打印堵住控制台，见第 11 节 |

### 4.6 内核配置里钉死的项

由 `config/dagu.fragment` 等片段决定，`build-kernel.sh` 合并后逐项断言，丢了就直接报错退出。

| 配置 | 原因 |
|---|---|
| `ARM64_VA_BITS_39` | 和原厂 4.19 一样三级页表；处理器不支持 52 位，48 位也被脚本拒绝 |
| 关 `KVM` | 主线会想占异常等级 2，和监控程序打架 |
| 关 `EFI` / `EFI_STUB` | 原厂内核不是可执行映像格式，带这个头会让引导程序读错设备树指针 |
| 关 `PTR_AUTH_KERNEL` / `BTI_KERNEL` | 对齐原厂 |
| `SM_GCC_8250=y` | 默认配置里没有全局时钟控制器，ginkgo 也踩过同一个坑 |
| `QCOM_WDT=y`（内建） | 引导程序留着看门狗，做成模块的话约 2 秒就复位 |
| 关 `POWER_RESET_MSM` | 开着时内核一崩约 2 秒回兔子 |
| `POWER_RESET_QCOM_PON=y` | 配合设备树 `mode-bootloader`，`reboot bootloader` 才有效 |
| `PSTORE_RAM` | 预留内存 `ramoops@b0000000` 4 MiB |
| 关 `INTERCONNECT_QCOM_SM8250` | 见第 7 节 |
| 关 `BOOTPARAM_HUNG_TASK_PANIC` | 闪存查询属性有时会在不可中断睡眠里停 10 秒以上，开着会把桌面打崩 |
| 关 `FUNCTION_TRACER` | 每个函数插空指令，会扰动 120 Hz 显示流压缩；只开普通事件跟踪 |
| 开 `DEBUG_INFO_BTF` / `KPROBES` | 给 bpftrace 用，需要主机 `pahole` ≥ 1.22 |
| 闪存、闪存物理层、显示等关键驱动内建 | 模块放在 userdata 上，根文件系统挂上之前用不了 |

早期看门狗：`overlays/linux/drivers/watchdog/qcom-wdt-early-dagu.c` 在 `early_initcall` 里把看门狗（`0x17c10000`）的咬合时间拉到 30 秒。咬合计数只有 20 位，超过约 32 秒会回绕成很短的值。内存盘的 `init.c` 在 `switch_root` 之前用魔术关闭的方式交出看门狗，否则进 Ubuntu 约 30 秒后会被咬回兔子。

绝对不要在 `head.S` 的 `primary_entry` 里、内存管理单元还没开的时候写看门狗或者插电源状态协调接口的复位调用：会立刻同步错误或者秒回兔子。`build-kernel.sh` 遇到带这种探针标记的树会直接拒绝编译，并强制 `DAGU_PRIMARY_ENTRY_PROBE=0`。

### 4.7 早期设备模式拓扑

- 保留 elish 的父子节点写法 `qcom,dwc3`（走 `dwc3-qcom-legacy.c`），不要改成合并式 `qcom,snps-dwc3`。
- 高速物理层是 `PHY_QCOM_USB_SNPS_FEMTO_V2`，必须内建。做成模块时控制器一直等不到物理层，电脑上什么都看不到。
- 最终控制台是内建的 `g_serial`。配置文件系统里绑网卡小工具会抢走控制器，`ttyGS0` 就再也带不出日志。

### 4.8 按“多少秒回兔子”判断死在哪

刷完发 `reboot` 后在电脑上看 `lsusb`：

| 现象 | 含义 |
|---|---|
| 约 3–6 秒回 `18d1:d00d` | 引导程序没跳（载入错误），或者内核入口立刻同步错误 |
| 约 20–25 秒回 | 看门狗咬了，或者老内存盘去碰 4.19 的小工具把内核打死 |
| 40 秒以上没有任何设备、也不回 fastboot | 内核跳进去了而且在喂狗，只是小工具没起来。只能长按电源 |
| `0525:a4a7` 稳定超过 30 秒 | 合格 |

## 5. 构建、刷机、救砖

### 5.1 构建

```bash
cd linux-mainline
./scripts/setup-deps.sh
./scripts/setup-kernel.sh          # 浅克隆 v7.0 到 linux/
./scripts/stage-firmware.sh        # 从 dumps 解出固件，不入库
DAGU_MINIMAL=1 DAGU_DISPLAY=1 ./scripts/build-kernel.sh
./scripts/build-bootimg.sh
ROOT_PASSWORD=... ./scripts/build-rootfs-desktop.sh
```

- 日常内核必须带 `DAGU_MINIMAL=1 DAGU_DISPLAY=1`。不带的话断言会报“`INTERCONNECT_QCOM_SM8250` still on”退出。
- 片段合并顺序：`dagu.fragment` → `dagu-bringup.fragment`（`DAGU_MINIMAL=1`）→ `dagu-usb.fragment` → `dagu-display.fragment`（放在可选项最后，好把前面打开的简单帧缓冲再关掉）→ 两个高通串行引擎片段 → `dagu-net.fragment`（第六版互联网协议和 Docker 网络内建）→ `dagu-bpf.fragment`。
- 显示构建会顺带编视频编解码模块，放到 `out/modules/venus/`。这三个模块每换一次内核都要重编：`#170` 上加载 `#169` 的模块失败，因为模块结构体大小变了。

### 5.2 补丁重放机制（`apply-overlays.sh`）

- 整文件驱动：`install_src` 从 `overlays/linux/` 拷进内核树，源文件缺了就退出。
- 原地修改：约 285 处 Python `text.replace()`，每处都带一个 `dagu: …` 标记，已经改过就跳过；要找的上下文不存在就报错退出。这保证重放是幂等的，也保证上游改了上下文会立刻暴露。
- 内容守卫：对拷进去的文件 `grep -q` 必须存在的符号或注释，例如键盘驱动必须包含鬼键过滤头文件，回环驱动必须保留会议软件需要的那几段逻辑。删掉一段关键修复，编译前就会被拦下。
- 坑：干净的 7.0 树里本来就没有某些老标记，硬退出会挡住重建，`1994fd3` 把这类改成警告。
- 坑：`readelf -S vmlinux | grep -q .BTF` 在 `pipefail` 下会误报失败，因为 `grep -q` 提前关管道，`readelf` 收到断管信号。`fb5c457` 改成 `grep … >/dev/null`。

### 5.3 刷写工具 `fb-usb.py`

谷歌 platform-tools 37 的 `fastboot` 在这台 AMD 锐龙主机的主控上会卡在 `USBDEVFS_REAPURB`；`fwupd` 还会把 `18d1:d00d` 认成移远的 4G 模块。`fastboot devices` 只读描述符，所以看起来正常。

`linux-mainline/scripts/fb-usb.py` 的做法：

- 用 libusb 独占设备，先把残留的输入包读空。
- 下载按 256 KiB 一块发，最后一个字节单独发一次，避免任何一次传输恰好是 512 的倍数（零长包会把这个主控卡死）。
- 超时重试 3 次；读 `max-download-size`，默认 768 MiB。
- 文件大于单次上限时自动切稀疏块；切片里不用“不关心”块，因为日志区里残留的安卓字节会把 ext4 搞坏。
- `reboot` 只等 2 秒：引导程序收到重启后直接断开，从不回 `OKAY`。

可选主机加固：`host-usb-fix.sh`（停 `fwupd`、关链路电源管理、装 udev 规则，下载卡住时给端口断电约 8 秒）和 `host/99-dagu-fastboot-nolpm.rules`。

### 5.4 日常刷机

```bash
ssh root@<平板地址> reboot bootloader
# 等电脑上出现 18d1:d00d，且序列号是 ab22268c
WAIT=20 ./scripts/flash-boot.sh flash-b
timeout 3 python3 scripts/fb-usb.py reboot
# 等 0525:a4a7 出现并保持 30 秒以上
```

`flash-b` 依次写 `dtbo_b`（存根）、`vbmeta_b`（关校验）、`vendor_boot_b`、`boot_b`，再 `set-active b`。A 槽保持第三方恢复系统或原厂。

规矩：

- 只刷 B 槽。不刷 `xbl`、`abl`、`super`。
- 从 Linux 回 fastboot 用 `reboot bootloader`；从安卓用 `adb reboot bootloader`，不要 `adb reboot fastboot`（那是用户态 fastbootd，刷不了 `boot_b`）。
- `reboot` 不会有 OKAY，不要等“Rebooting…”。每 2 秒看一次设备：看到 `18d1:d00d` 就马上刷；看到 `0525:a4a7` 说明 Linux 起来了。
- userdata 刷成 Ubuntu 以后，不要让引导程序去启动当前槽的安卓内核，它挂不上 ext4。
- 历史：早期只写 A 槽时，小米会从 B 槽恢复，表现成“刷了没生效”；两槽都刷成主线后，看门狗热复位又会进同一个内核，开机图看起来永远冻住。所以最后定成“只刷 B、A 留救援”。

根文件系统：`flash-rootfs.sh` 只写 userdata（8 GiB 镜像，`fb-usb.py flash -S 256M`）。第一次开机由 `init.c` 按分区名 `userdata` 找盘，在没挂载时跑 `e2fsck` 和 `resize2fs` 扩到整盘，再挂载、`switch_root`。userdata 还是安卓的 f2fs 时，留在内存盘里，提供远程登录。

### 5.5 救砖阶梯（主线开发期间）

1. 长按电源约 10 秒，再按住音量下开机，进 fastboot。只短按电源会再次进 7.0 卡住。
2. `flash-boot-legacy.sh restore-a`：A 槽写回原厂 `dtbo`、`vendor_boot`、`boot`、`vbmeta` 并设为活动槽。
3. `flash-boot.sh restore`：两槽都写回原厂。
4. 最后手段：9008 紧急下载模式刷官方 `flash_all`，绝不能上锁。

开发期遇到过的“回兔子”根因（都能从 fastboot 救回）：

- 秒回：空叠加分区、4 份拼接、活机设备树、主线设备树没带符号表、入口探针、内核崩溃时走 `POWER_RESET_MSM`、看门狗做成模块。
- 约 25 秒：老内存盘碰 4.19 小工具。
- 进 Ubuntu 约 30 秒被咬：`switch_root` 关看门狗没写魔术字符。
- 约 24 秒硬锁：6 号核空闲态。
- 硬复位：把 `vreg_l3a_0p9` 改成 1.104 V（那是核心电源轨）。
- 回兔子：给高通串行引擎包装层写固件或写包装层寄存器。
- 关机挂死：`#437` 远程调用缓冲释放空指针（`e83d17d`）。
- 08-30：内核跳进去了但电脑上 40–50 秒什么都没有，原因是改成合并式控制器节点加物理层做成模块。

### 5.6 7 月的紧急下载模式事件

细账：`docs/dagu-edl-recovery-full-playbook.md`、`docs/why-boot-modification-caused-dead-device.md`、`docs/dagu-recovery-and-brick-record.md`。

经过：Windows 路线的统一可扩展固件接口镜像是个半成品（内存布局抄自别的机型、控制器节点不匹配、帧缓冲步长错、内存表写坏导致退出引导服务后崩溃）。退出引导服务以后，那个自编的 Linux 大容量存储内核崩溃或挂住，没有打印、没有串口、屏幕也关了。启动 0.5 秒后自动切大容量存储，把数据线从 fastboot 抢走，电脑丢了设备。反复靠按键救，最后按到了紧急下载模式组合键。

事后核对：整个过程没有往闪存写过任何持久内容（全是 `fastboot boot`，计划中的分区表修改因为大容量存储从没枚举出来而没发生），唯一的持久写入是解锁本身。“看起来像砖”其实是内存里挂死加上紧急下载模式的授权门槛。

救回步骤：

1. 修 MiFlash 20220507（建 `log`、`restore`、`tmp` 目录，去掉幽灵设备）。
2. 修 9008 驱动代码 52（换 oem48.inf）。
3. 拔线、长按电源 30 秒、插 2.0 口，拿到新鲜的紧急下载会话。Sahara 报“只读到 0 字节”就是会话超时；正常会看到 `736052 bytes transferred`。
4. 原厂烧写程序要小米服务器签名授权（报 `Only nop and sig tag can be received before authentication`），和是否解锁无关。换社区解锁版 SM8250 烧写程序（和 Poco F3 同名 `prog_ufs_firehose_sm8250_ddr_5.elf`），或者用打过补丁的 MiFlash。
5. MiFlash 紧急下载模式选“全部删除”刷 `dagu_images_OS2.0.10.0.ULZCNXM_14.0`，约 345 秒成功。事先把 `flash_all_lock.bat` 改名禁用。
6. 拔线、强制关机、开机（首次 5–15 分钟），确认 `unlocked: yes`、`product: dagu`。

事后定下的纪律：挂住时先长按电源 30 秒再考虑紧急下载模式；进紧急下载模式之前先备好解锁版烧写程序；一次只改一个变量；关掉自动大容量存储；保证有串口或屏幕控制台；内存布局要和真机 `/proc/iomem` 对过。

## 7. 平台层的共性坑（高通虚拟机监控程序）

这些坑不属于某个外设，而是这台机器的固件环境决定的。很多外设的问题最后都落在这里。

| 坑 | 现象 | 做法 |
|---|---|---|
| 片上互连带宽投票 | 一开 `CONFIG_INTERCONNECT_QCOM_SM8250`，总线时钟管理器的批量写永远等不到完成，拖死设备模式控制器、显示控制器、处理器调频 | 配置里关掉，设备树在处理器 0–7、显示、设备模式控制器、闪存、视频编解码、相机、串口 6 上删掉 `interconnects`。引导程序已经为开机画面训练好了显示带宽。视频编解码另打桩（第 12 节） |
| 高通串行引擎包装层 | 给 `&qupv3_id_0/1/2` 写 `firmware-name` 或写包装层寄存器，整机回兔子 | 每个用到的串行引擎只把原厂 `qupv3fw.elf` 装进自己的指令内存，并带 `qcom,skip-wrapper-fw-init`。`0e55f23` 的结论是“挂死的是包装层寄存器，不是串行引擎本身”。蓝牙串口 6、功放、触控、背光、电量计、键盘、电荷泵都用这个模式 |
| 通用直接内存访问 | `CONFIG_QCOM_GPI_DMA` 是另一块在这套固件下碰不得的寄存器 | 关掉；串行外设接口走队列模式 |
| 核心电源轨 | `vreg_l3a_0p9` 改成 1.104 V 硬复位 | 不改 |
| 处理器空闲态 | 6 号核掉电后回不来 | `cpuidle.off=1` |

## 8. 显示

细账：`dagu-adaptation-status.md` 显示一节、`dagu-idle-pipeline.md`。驱动：`overlays/linux/drivers/gpu/drm/panel/panel-xiaomi-dagu-l81a.c`。

### 8.1 面板

- L81A，`l81a_42_04_0a_dual_dphy_video`。两路显示串行接口各 4 线差分物理层，视频模式，显示流压缩 1.1，切片 800×20，每包 1 片，8 位色深、每像素 8 位。
- 初始化序列和 800+800 时序来自高通的 `dsi-panel-l81a-42-04-0a-video.dtsi`。命令发送照 elish NT36523 驱动用双路辅助函数；显示流压缩参数集按高通 `dsi_panel_update_pps()` 的做法，在亮屏命令（`0x11`/`0x29`）之后发，每路宽度减半成 800。
- 关键细节：
  - 时序要写成整幅模式：水平前沿 / 同步 / 后沿 120/80/120（单路是 60/40/60），因为双路拆分会再减半。直接照抄高通的单路数字，每路就只剩 30/20/30，压缩流是黑的。
  - `0xb2` 命令第 3 字节 `0x40` 是面板侧的压缩使能，少了它黑屏。
  - 准备阶段要先把 100 号引脚（触控复位 `tp-reset`）拉高再复位面板，否则触控显示一体芯片停在复位态，背光亮、画面黑。
  - 只登记 120 Hz 一个模式。登记同名 60 Hz 时桌面会选 60；用减半像素时钟做 60 Hz 时双路会闪。
  - `disable()`、`unprepare()` 是空操作：这条视频模式链路上发关屏命令会超时，之后也重放不了初始化，屏就再也亮不了。
- 设备树：两路显示串行接口都删掉 `qcom,sync-dual-dsi`，否则主线会跳过 0 号口的发送。

### 8.2 背光

- 两颗 KTZ8866，驱动 `ktz8866.c`。产品路径走高通串行引擎 11 和 9 的芯片间总线（按第 7 节的单引擎固件模式）。
- 引导程序已经编程过背光芯片，139 号使能引脚整次开机都不能拉低，拉低芯片就复位、屏黑到下次开机。不要像 elish 那样把它绑成 `enable-gpios`，它归面板驱动管。
- 桌面只看到一个 `l81a-wled`，滑条按二次曲线映射后同时写两颗。滑条拉到 0 时仍保持 11 位下限 32，不然完全看不见。
- 熄屏是真黑（`#630`）：显示关闭、`bl_power` 关、面板重新初始化、关机充电开机这几种“熄屏”状态下，驱动清掉背光芯片的灯串使能位（`ktz8866_led_off()`），139 号使能引脚不动。以前熄屏只是降到下限 32，屏幕还微微发亮。
- 开机白屏（`#630`）：第一次初始化面板时，复位和初始化命令是在引导程序留下的背光还亮着的时候发的，从复位到第一帧压缩画面之间，面板输出的是行缓冲里的杂乱内容，看起来是一下白色花屏。安卓是先出第一帧再开背光。现在第一次复位之前就关灯，视频起来后再等 100 毫秒开灯。

### 8.3 显示处理单元和压缩

| 问题 | 根因 | 修复 | 结果 |
|---|---|---|---|
| 桌面花屏 + 触摸断续 | 合成器扫出 10 位色的 `XR30`，但面板压缩是 8 位；再加上全屏重绘调试变量拖死输入 | `#149` 去掉 10 位图层格式；去掉重绘调试变量 | 主帧缓冲 `XR24`，修饰符 `0x0500000000000001`（高通带宽压缩） |
| 双路下链路锁不住 | 拆分模式里按每路 800 宽计算时截断成 266 | 改成向上取整 267 | 稳定 |
| 偶发 `vblank timeout: 400000` | `0x400000` 是第 22 位，即压缩块的刷新位，不是幽灵光标图层；视频模式下空闲 58 毫秒会关中断，饿死下一次提交并和双路压缩刷新赛跑 | `#171`：视频模式不进那段延迟关中断（标记 `dagu: video mode keep IRQs`） | 进入空闲 0 次，超时 0 次 |
| 每次提交都重做压缩准备 | 主线每帧重写参数集、重新绑定、重设刷新位 | `#175`：没变就跳过（`dpu-skip-redundant-dsc-prep.patch`） | 只解释少数 100–200 毫秒的内核侧等待，不是主卡顿源 |

硬件限制：SM8250 的显示处理单元没有图层内旋转。横屏是合成器逻辑上转 270°，内核这边 `rotation=1`（不转），最大化窗口只能走合成器的整窗合成，不能直扫到第二块图层。

### 8.4 字体和缩放

- 支持的缩放：1.0 / 1.25 / 1.333 / 1.667 / 2.0 / 2.5 / 2.667（没有 1.5）。日常 1.25。不要锁死 2，不要关 `WaylandFractionalScaleV1`：关了以后 Chromium 只按整数像素比栅格化，合成器再缩一次，1.25 下字会糊成“乱码”。
- 270° 扫描下液晶的红绿蓝子像素排在了错的轴上，字体必须用灰度抗锯齿：`--disable-lcd-text`、`--font-render-hinting=none`、`99-dagu-gray-fonts.conf`（`rgba=none`）。
- 量化：`scripts/dagu-fb-score.py`。计分读内核显示状态，不要信桌面起来后的 `/dev/fb0`。

## 9. 图形

细账：`dagu-a650-linear-destile.md`、`dagu-wifi-gpu-turnip-cpu.md`、`dagu-vulkan-truth.md`。

### 9.1 点亮

- `&gpu`、`&gmu`、`&adreno_smmu` 打开。
- 安全着色器用本机签名的 `qcom/sm8250/xiaomi/dagu/a650_zap.mbn`，不能用 elish 的。
- 命令处理器微码必须是 linux-firmware 里那份 `a650_sqe.fw`（31964 字节，第 2 个字 `0x112`）。dump 里的老版本会被内核拒绝。
- 结果：`/dev/dri/card0` + `renderD128`，桌面走硬件合成，不是软件渲染。Vulkan 驱动报 `Turnip Adreno (TM) 650`，一致性版本 1.2.7.1，Vulkan 1.3。
- Khronos 一致性测试（2026-09-11）：冒烟 6/6、版本 3/3、设备初始化 216 通过 8 不支持、计算基础 66 通过、绘制 4/4 和 160/160，0 失败。
- 频率：305–670 MHz 七档。调速器只有 `userspace` 和 `simple_ondemand`，写 `performance` 返回 `EINVAL`。空闲下限钉在 587 MHz，触摸或播片时由 `dagu-touch-boost` 抬到 670。

### 9.2 网页毛玻璃花屏（两层合同）

现象：Chromium 里网页毛玻璃效果（背景模糊）整卡雪花、字形变成 1 位方块，而元素自己的模糊是好的。

第一层，窗口系统撒谎：Chromium 分配缓冲时给的是“线性 + 高通压缩 + 高通分块”候选，但通过 Wayland 告诉合成器时永远写修饰符 0（线性）。像素实际是分块的，按线性去读就是雪花。

- 当时的绕法：`scripts/dagu-linear-mod.c` 预加载库，只把任一边超过 1024 的窗口级缓冲做成真线性；小图集原样分块（全部逼线性会把字体图集打成 1 位砖）。
- 2026-09-13 撕掉这层合同：自编的 Chromium 152 把真实修饰符交给合成器，窗口直接是高通带宽压缩格式，不再预加载那个库。

第二层，线性目标在片上图形内存里写不对：Mesa 的事件存储把线性目标写成了宏分块，二维拷贝引擎也不是解分块器。

- 根因来自在 HyperOS 板上逆向官方驱动：抓到的 16 字解析命令包显示官方用的是 `BLIT_EVENT_STORE_AND_CLEAR | CLEAR_MASK=0xf | LAST=2`，同时写 `RB_RESOLVE_CNTL_0=0`、片上内存基址 0、并发解析。
- 第二个错：同批次读帧缓冲时，Mesa 把采样地址指到片上内存基址加偏移（`0x100000`），而 Adreno 650 的统一缓存要从偏移 0 读。
- 两个正式补丁：`patches/0001-freedreno-a6xx-fix-event-store-linear-layout.patch`、`patches/0002-freedreno-a6xx-fix-gmem-fb-read-linear-base-offset.patch`。绘制和读取之间要刷颜色缓存再失效，不能用另一个失效命令。
- 结果：片上内存的存储、恢复、同批次读取都是真线性，测试页 A–H 卡片都是真霜。

后续几个同类问题：浏览器自己的矢量图标（后退、刷新、关标签，128² 以内的缓存）被画成分块却按线性采样，改成线性加片上内存；路径图集保持分块并强制走片上内存；整窗 2477×1560 不要强制片上内存（每帧 15 个分箱，拖动掉帧）。`6f1b2f9` 把“哪种尺寸用线性”的规则写成了 `scripts/dagu_glass_layout.py` 和单元测试。

规矩：

- 打过补丁的 Mesa（`/usr/local/lib/dagu-mesa/`）只给 Chromium 和 Mineradio。永远不要给 gnome-shell 加这个库、加线性预加载、加 `FD_MESA_DEBUG=notile/sysmem`、加 `DAGU_LINEAR_SYSMEM`（线性加模板缓冲走系统内存会把扫描输出写黑）。
- 全局 `notile` 会让没用深度缓冲的分块 WebGL 卡死颜色缓存，报 `00800005`。
- 禁止 `--disable-gpu-rasterization`、禁止关网页毛玻璃、禁止用软件渲染“修”。

### 9.3 还没解决

偶发 `gpu fault status 00800005`（命令流故障）后会自动恢复。不是温度问题：空闲 50–58 °C，毛玻璃压测约 80 °C、670 MHz 时恢复计数也没变。`scripts/dagu-gpu-hangwatch.sh` 盯着它，发生时自动转储。

## 10. 桌面滑动卡顿

细账：`dagu-idle-pipeline.md`（50 节）、`dagu-identity-kickoff-hole-problem.md`、`dagu-typeb-kickoff-hole.md`、`dagu-scroll-jank.md`。

### 10.1 现象和定性

B 站首页慢慢滑，画面会“抽”一下。量化工具 `scripts/dagu-dpu-jank-capture.py` 用事件跟踪同时记垂直同步回调和显示提交：

- `#170` 基线：垂直同步 1494 次，间隔中位 8.33 毫秒，没有一次超过 16.7 毫秒；但提交的第 99 百分位 79 毫秒，最长 151 毫秒，超过 50 毫秒的空洞 18 个。
- 空洞里垂直同步照走，屏在 120 Hz 重扫旧帧。所以不是屏卡、不是压缩超时，而是“没有新帧提交”。

再往下排除：

- 不是图形处理器降频：空闲下限已经是 587 MHz，处理器钉满频率也拉不走长帧。
- 不是内核栅栏卡住：对洞做对齐，内核里没有活着的等待，最长等待 2–7 微秒，`complete_flip` 和提交 1:1。主线显示处理单元的输出栅栏按提交收，不按扫屏收；没有新提交就不会有新栅栏要发。
- 不是触摸：注入的触点和网页收到的事件 1:1，没有超过 20 毫秒的缺口。

结论：空洞里图形处理器忙碌度掉到 0，合成器在 `poll_schedule_timeout`（帧时钟停车），Chromium 的图形线程在 `futex_do_wait`（等合成器的帧回调或缓冲释放）。双方互相等。

### 10.2 根因

`scale-monitor-framebuffer` 实验特性在 270° + 1.25 缩放下，会把最大化的 Chromium 窗口的“未被遮挡区域”算成空。`update_area` 看到空区域直接返回，损坏区域被丢掉，帧回调也不发。合成器以为没东西要画，Chromium 在等回调，就空等 80–180 毫秒。

修复：把 `org.gnome.mutter experimental-features` 设成空，再让 gnome-shell 重读。之前有一次只改设置没重启外壳，特性其实还在跑，那次结论作废。

| 窗口 | 条件 | 慢滑提交频率 | 最长 / 超过 50 毫秒 |
|---|---|---|---|
| `071722` | `#170` 基线 | 62.8 Hz | 151 毫秒 / 10 |
| `073051` | 触摸时让合成器重画 | 99 Hz | 93 毫秒 / 1 |
| `074651` | 首页慢滑基线 | 87 Hz | 178 毫秒 / 4 |
| `095339` | 缩放特性还开着 | — | 32 个空洞 |
| `100147` | 关掉缩放特性 | 91.4 Hz | 103 毫秒 / 3 |
| `102725` | 5 路硬解视频页面 | 104.1 Hz | 41.6 毫秒 / 0（第一次清零） |

Chromium 152 上另外改了几处（`patches/chromium-152-dagu-scroll-interlock.md`）：把屏幕刷新率从 Wayland 输出事件传给帧调度，缺省按 120 Hz；默认帧间隔 120 Hz；关掉“首选帧间隔”（一个 60 帧的视频曾把整个页面的动画回调钉在 16.7 毫秒，改后中位 8.3 毫秒、111 帧）；滚动时优先流畅度而不是等新内容。

### 10.3 否决过的实验（都更差，都撤了）

- 16/24 毫秒令牌、卡住看门狗：慢滑 4.1 Hz，最长 768 毫秒。
- 让合成器给非主视图也发帧回调（改 `0x1673c8`）：52–56 Hz。
- 未遮挡区域为空时改成整窗重画：最长 341 毫秒。
- 提前强制释放缓冲（预加载库改 `dec_use_count`）：最长 658–986 毫秒。Chromium 复用了合成器还在读的缓冲。
- 关显式同步：更差。
- `--double-buffer-compositing`、外部帧源、`governor=performance`（芯片约 75 °C）、关图形栅格化：都更差或不允许。
- 竖屏原生方向 + 1.0 缩放 + 全屏：仍然只有一块图层，空洞还在。

### 10.4 还开着的“Type B”空洞

在纯 GTK（GIMP Toolkit，GTK 图形工具包）实验室（合成器不旋转、1.0 缩放）里，原版提交频率约 115 Hz，每 8 秒仍有 2–4 个超过 50 毫秒的洞。机制：mutter 50.1 `on_after_update()` 在翻页之前就把帧回调发掉并拆了源，翻页后时钟停在空闲，而客户端冻结在等下一个回调。七个 mutter 变体最好约 110 Hz，都没到“120 Hz 且 0 空洞”的验收线。现在保留两处活补丁（`mutter-50-queue-callback-wakeup.patch`、精化后的 `mutter-50-msm-no-explicit-infence.patch`）。下一刀的方向写在 `dagu-identity-kickoff-hole-problem.md` 第 109 节。

## 11. 触控

细账：`dagu-touch-irq-jitter.md`。驱动：`overlays/linux/drivers/input/touchscreen/himax-dagu.c`。

- 硬件：Himax HX83121，中断在 39 号引脚，低电平触发。
- 总线：高通串行引擎 4 的串行外设接口，队列模式（8–11 号引脚），按第 7 节单引擎固件模式；通用直接内存访问禁止。板上日志：`geni_spi 990000.spi: dagu SPI FIFO proto=1 depth=16 width=32 fifo_if_dis=0 skip_wrap=1`。早期用引脚模拟的串行外设接口节点 `himax_spi` 保持关闭。
- 不要把触控绑到 100 号引脚：那是面板的触控复位脚，归面板驱动。

| 问题 | 根因 | 修复 |
|---|---|---|
| 滑动断触 | 中断线程里 `dev_info`，在 `ignore_loglevel` 下堵住屏幕和串口控制台；边沿触发丢中断 | 去掉打印；改低电平触发；全 `0xff` 坏帧不当抬手 |
| 屏幕键盘连打字母 | 低电平触发下一次按住里会读到校验失败或 0 点的毛刺，跟踪号被拆成多次点击 | 中断里排空读取、校验和、连续空帧才抬手，80 毫秒超时兜底 |
| 中断全落在 0 号核 | 和显示、图形、视频、闪存挤在小核上 | `dagu-himax-irq-affinity.service` 绑到 4–7 号核 |
| 开 Snapshot 后置摄像头时点不动 | 1200 万像素的软件去马赛克把合成器饿死 | 拜耳跳采、软件处理限 0–3 号核、不常驻双路采集（现在已改走硬件通路） |

驱动在触摸时用频率服务质量把三簇处理器和图形抬一档（180 毫秒）。注意 `dagu-himax-swipe.py` 是往事件节点里写合成触点，不能用来判断芯片时序。

## 12. 视频编解码

细账：`dagu-venus.md`、`dagu-chrome-gpu-venus.md`。

### 12.1 点亮

- 探测卡在 `core.c` 里 `devm_of_icc_get("video-mem")` 返回推迟探测，因为没有 SM8250 的片上互连驱动。
- 修法：设备树删掉视频编解码节点的 `interconnects`，`of_icc_get()` 就返回空而不是错误；`icc_set_bw(NULL)` 是空操作。补丁 `patches/kernel-sm8250-venus-icc-stub.patch`，重放标记 `dagu: ICC video-mem stubbed`。
- `CONFIG_VIDEO_QCOM_VENUS=m`，`CONFIG_SM_VIDEOCC_8250=y`。固件用本机签名的 `qcom/sm8250/xiaomi/dagu/venus.mdt`，不能用 elish 的 `venus.mbn`。
- 模块不自动加载（可信区认证失败时只让模块失败，不拖累启动），由 `dagu-venus-load.service` 加载。
- 结果：`/dev/video14` 解码（H.264、VP8、VP9、高效视频编码、MPEG-2（Moving Picture Experts Group 2，动态图像专家组第 2 代标准）→ 线性或高通压缩格式），`/dev/video15` 编码（→ H.264、VP8、高效视频编码）。

### 12.2 上屏

| 场景 | 结果 |
|---|---|
| 1080p H.264 不上屏 | 10 秒片子 1.68 秒解完（约 180 帧每秒） |
| 1080p 经 `waylandsink` | 协商到共享缓冲 `DMA_DRM` / `NV12`，零拷贝；8 核总占用约 5.9% |
| 4K60 高效视频编码 | 不上屏约 57 帧每秒；上屏 10 秒片子正好 10.000 秒播完，占用约 8.1%；无内存管理单元错误、无子系统重启 |

## 13. 音频

细账：`dagu-adsp-voice.md`、`dagu-adsp-voice-pipeline-status.md`、`dagu-audio-s2idle.md`。

### 13.1 扬声器

```text
MultiMedia1 hw:0,0 → TERT_TDM_RX_0（音频前端 0x9020）→ 时分复用组 0x9120 → 4 颗 CS35L41
```

- 音频数字信号处理器固件 `qcom/sm8250/xiaomi/dagu/adsp.mbn`；需要 `CONFIG_QRTR_SMD=y`，做成模块时保护域和音频包路由起不来。
- 功放走高通串行引擎 1 和 3 的芯片间总线。
- 流格式：双声道 24 位、48 kHz，装在 32 位时隙里，4 个时隙。
- 四颗功放内置处理器都写到校准状态 2（左上 9524、右上 9632、左下 9497、右下 9696），灌了音乐场景参数；H 类跟踪和安卓一样（`Enable=1`、`Target=0`）。

| 问题 | 根因 | 修复 |
|---|---|---|
| 音量拉满也很小 | 功放只写到校准状态 1；时分复用组的位宽用了时隙宽度 32，音频数字信号处理器把数据当 32 位样本，高 8 位是空的，约 −48 dB | `07e4c7e`：位宽用样本宽度（16/24），时隙仍 32。强行 32 时音频前端报参数错误。禁止用软件音量或数字增益“补响” |
| 桌面只有“虚拟输出” | PipeWire 的声卡配置认不出音频数字信号处理器的混音器，停在关闭；专业音频配置会把设备开成 8 声道 | 写用例管理器配置 `alsa/ucm2/Xiaomi-dagu/HiFi.conf` 和 `conf.d/sm8250/…`；用例里的控件名必须用内核控件全名，少一个整个用例就失败 |
| 整段会话没声音 | PipeWire 配置里直接打开 `hw:0,0`，登录瞬间声卡还没出现，PipeWire 以 234 退出，套接字被 systemd 限频，6 小时都没恢复 | 撤掉那份配置；`dagu-audio-up.sh` 等声卡和编解码控件都出现再拉起 PipeWire；放宽重启限频 |
| 每次开机音量变 100% | 启动脚本自己设音量 | `1db7637`：交给 WirePlumber 记住 |
| 刷屏把桌面卡住 | 主线 `q6asm_dai_prepare` 打开失败就释放客户端，PipeWire 在同一个句柄上反复准备，每秒几百行错误；关闭时又只在运行态才发关闭命令，泄漏会话 | `56a4ef1`：客户端跟句柄同寿命；关闭总是发关闭命令 |

WirePlumber 配置 `alsa/50-dagu-speaker.conf` 要点：用用例管理器、不自动选口、不开专业音频、不拆分；软件音量（桌面滑条从不碰芯片数字增益）；把蓝牙卸载那个设备（`alsa.device="3"`）的输出禁掉，否则探测时会反复打开那个音频前端口刷错误。一个匹配对象里的条件是“且”，数组里两个对象是“或”，写错一次就把所有输出都禁了。

### 13.2 麦克风

```text
WCD9385 模拟麦 5（偏置 3）→ ADC4 INP5 → TX DEC0 → TX_CODEC_DMA_TX_3（音频前端 0xb037）
```

- 路由照安卓 `mixer_paths_overlay_static.xml` 的免提麦。主线还要额外打开 `ADC4 Switch` 和 `TX3 MODE=ADC_NORMAL`，安卓在编解码驱动里做了这一步。

- 回归测试：`tests/test_dagu_mic.py`。

- 反向文件系统里 `..` 重复分配导致关闭报错。

## 15. 充电和电池

细账：`docs/dagu-67w-充电方案.md`、`docs/xiaomi-charge-public/`。

### 15.1 电量计

- 两颗 BQ27Z561，高通串行引擎 0 和 13 的芯片间总线。驱动 `xiaomi-dual-fg.c` 合成 `bms`：电量按两颗剩余容量之和除以满容量之和，原始值 96.00% 以上显示 100%；电压取较高的一颗，电流和容量相加。

### 15.2 5 V 路径

- 驱动 `pm8150b-charger-dagu.c`：主线的充电驱动是上一代，换算系数不对（这颗输入限流和充电电流每格 50 mA，浮充 3.6 V + 每格 10 mV）。关充电器看门狗、解除输入挂起、清掉引导程序留下的潮湿检测，74 号引脚拉低放行总线电压。浮充 4.48 V。

| 提交 | 问题 | 修复 |

| `7e5cf82` | 100 瓦充电宝接受 9 V 后，电源切换期间总线电压掉了一下，端口管理器当成拔线，在 2.2–2.8 V 之间循环 | 接收端只报 5 V / 2 A；等协议类型确定后再设限流；切换期间忽略那次掉电。结果：协议谈成、限流 2 A、电池约 +760 mA，充电宝约 8.6 瓦 |

### 15.3 67 瓦（9 V 锁定）

这台的事实：

- 两节并联，电池电压约 4 V，不是串联。
- 小米认证用厂商识别号 `0x2717` 的非结构化厂商自定义报文，摘要核对后，充电器把可编程电源的电流从 5 A 改成 6 A；拔线后忘掉。
- 67 瓦是原装头的铭牌（11 V × 6.1 A），平板不会为了凑这个数去要 11 V 以上。
- 原厂策略（`pd_policy_manager_dagu.c`）：第一次请求两倍电池电压 + 700 mV；进电荷泵前以 20 mV 一步把总线调进“两倍电池电压 + 650 到 900 mV”的窗口；总线过压报警 9.5 V。

2026-10-22 的失败：认证和 6 A 都成功，第一次请求约 9.06 V / 6 A，电荷泵能开；随后“电流不够就加 20 mV”那一票一路加到约 10.5 V，电荷泵报故障退出，充电宝有时直接断开配置通道。实测总线贴着两倍电池电压，加电压并没有把电流加上去。

方案（`8cfb5ff`、`dcb8cb1`，内核 `#579`，v0.1.4）：

1. 插入先停 5 V，发认证，读能力；电流没升到 6 A 就重认证，最多 3 次。
2. 认证成功后先关降压充电器，再请求 9.000 V，电流取“刚报出的值、6200 mA、67 瓦除以电压”三者最小。
3. 从电荷泵先开，主电荷泵后开。
4. 全程锁 9.000 V，删掉加电压的那一票；接近 4.48 V、温度或电池电流到限时只降电流。
5. 认证失败、没有 6 A、9 V 没谈成、电荷泵故障、电荷泵自己关掉使能，都退回固定 9 V / 3 A 降压，拔线前不再进电荷泵。最后一种情况健康位仍是“正常”，不处理的话降压也停着，电池电流为 0，电量停住。

理论上限 9 V × 6 A = 54 瓦母线，约 50 瓦进电池。按 `README.md` 的 v0.1.4 记录，实测多数时候落在 9 V 降压路径，约 18 瓦，没到铭牌。还没移植：高通快充 3.5、再充阈值、截止电流、夜间充电、完整温度分段、电荷泵中断。融合快充规范 T/TAF 083-2021 走的是数据线上的另一套握手，不要和小米报文混在一起。

### 15.4 关机充电

`7e577c4`，`scripts/dagu_offmode_charger.py`，测试 `tests/test_dagu_offmode_charger.py`。

- 行为照 HyperOS：插线开机显示电量，45 秒后熄屏（实测 HyperOS 约 45 秒），短按电源点亮，长按 2.5 秒进桌面，拔线 15 秒后关机。直接画到 `/dev/fb0`，转 270°。
- 判断是不是“插线开机”只看确定的信号：引导程序给的 `androidboot.mode=charger`、充电类的启动原因、开机原因寄存器有插线位且没有电源键位。调试用的数据线会让充电器在线，“充电器在线”本身绝不能跳过桌面；遗留的待处理标记也不算。
- 关机就是真关机（`#630`）：插着线关机时，电源管理芯片看到有电会马上重新上电，引导程序带 `androidboot.mode=charger` 启动内核，这和安卓的关机充电是同一条路。关机一开始 `dagu-shutdown-display` 就关背光，所以点完关机屏幕立刻变黑，不会再露出登录界面。
- 以前的问题：有一个守护进程想在桌面里“拦下关机”，它持有关机延迟锁却只盯着定时关机的文件，从不释放。于是每次关机 logind 都要等满 `InhibitDelayMaxSec=20s`，这 20 秒里桌面会话先退出，显示管理器又把登录界面拉了起来，看起来就是“先回到锁屏，再关机”。现在守护进程删掉了，延迟恢复默认 5 秒；实测从发出关机到开始关机 14 毫秒，0.17 秒黑屏，约 2.8 秒断电。
- 关机充电开机时内核日志不上屏：面板驱动看到 `androidboot.mode=charger` 就一直关着灯，直到电池界面画好再由界面写 `/sys/module/panel_xiaomi_dagu_l81a/parameters/charger_dark` 开灯；进桌面的路径也会开灯。60 秒内没人开灯就自己亮，免得坏掉的启动什么都看不见。
- 电池界面先画再做慢的事：`systemctl mask` 每次都会重载 systemd，挪到画完之后。按从上电开始的计时，9.3 秒出电池（以前 12.3 秒），其中约 7.2 秒是芯片和引导程序。
- 关键教训（10-24 桌面起不来那次）：电池界面服务原来挂在多用户目标上，又写了和显示管理器冲突，systemd 每次开机都把显示管理器的启动任务丢掉，平板停在控制台刷日志。现在这个服务不挂任何目标，只由判断服务在确认插线开机时 `systemctl start --no-block` 拉起，它对显示管理器排的停止任务正好替换掉待启动的任务。

## 16. 休眠

- 只有浅休眠：`/sys/power/mem_sleep` 只有 `[s2idle]`，用 `echo mem > /sys/power/state`。
- 2026-09-12 第一次：睡约 65.5 分钟，电源键唤醒，成功计数 1；显示仍是高通带宽压缩、视频编解码和音频数字信号处理器都在、无图形挂起、无子系统重启；无线网络重新上电恢复。醒来后功放报一次 −110，声卡还在。
- 现在的产品路径：合盖（110 号引脚霍尔）和短按电源都进浅休眠。`systemd/logind-dagu-power.conf`：合盖和电源键都休眠，`HoldoffTimeoutSec=2s`（默认 30 秒会吞掉醒来后的下一次合盖）。GNOME 设置守护进程会拿着电源键的阻塞锁，所以动作要在 dconf 里也设成休眠；合盖时“有外接显示器也休眠”要打开，因为醒来后合成器重新探测会以为多了一块屏。
- 没有实时时钟，`rtcwake` 用不了；时间靠联网校时（没校时的话加密网页证书“尚未生效”，B 站只有文字没有样式，登录认证模块还会以为密码修改日期在未来）。
- 休眠钩子 `dagu-folio-resume`：睡前停传感器客户端，醒后再起。
- 不要远程 `echo mem`，旁边没人按电源键就醒不来；数据线上的串口小工具不能唤醒。

## 17. 无线网络和蓝牙

### 17.1 无线网络

- `1095132`：设置里点新的加密网络时会先断开当前网络、密码框又不弹。改成先弹框存密码再连接。

### 17.2 蓝牙

- QCA6390 走串口 6，`hci_qca`，单引擎固件模式。使能脚走电源序列驱动，节点上不要再写 `enable-gpios`（双重驱动），也不要写 `firmware-name`（错槽会覆盖校准文件）。
- 内核要 `CONFIG_UHID=y`、`CONFIG_BT_LE=y`（低功耗蓝牙人机接口设备）和 `CONFIG_BT_HIDP=y`（经典人机接口设备）。缺了的话设置里显示已连接，鼠标不动。

| 问题 | 根因 | 修复 |
|---|---|---|
| K380 键盘连上没有按键 | BlueZ 默认只接受已绑定的经典人机接口设备，而配对码要在键盘上输入、绑定之前就要放行 | `bluetooth/input.conf`：`ClassicBondedOnly=false`、`UserspaceHID=persist` |
| 按键很钝 | 默认嗅探间隔 50–500 毫秒 | 改成 3.75–11.25 毫秒（内核默认和配置都改），实测 12.5 毫秒。不要开省电标志：每次指示灯报告都退出嗅探，这颗芯片要约 200 毫秒，按键抬起会卡住变成自动连发 |
| 点连接超时 | 查询缓存超过 60 秒后，主线寻呼时把时钟偏移当 0 | 连接建立后读时钟偏移写回缓存；主机当主设备；交错页扫描；页超时 16384 |
| 鼠标在设置页一闪就没 | 低功耗扫描和经典查询同时跑，把经典查询饿死 | 去掉这颗芯片的“同时发现”特性，分时进行（和安卓一样） |
| 设置里“未设置”转圈、再点超时 | 已绑定设备配对返回“已存在”被当失败；未分配句柄的连接成了僵尸 | 重编 `libgnome-bluetooth`（`b5aac9c`）；清理僵尸连接；用户点击直接建低功耗连接，建之前先取消查询 |
| 鼠标连上 2 秒就断 | 交换最大传输单元前就请求了很短的连接间隔，控制器不带数据；内核默认监督超时 420 毫秒太短 | 等第一个属性协议包或 500 毫秒再更新参数（`3bbaf0c`）；监督超时 3 秒（`7cd802c`） |

BlueZ 侧另外设了设备类别为平板、临时设备保留 180 秒、总是可配对、隐私关闭；`dagu-bt-hid-host.sh` 在控制器复位后重新打开可连接和页扫描，并给已绑定设备写“可信”。不要用纯经典模式（会断掉低功耗鼠标），不要把人机接口设备放进自动重连列表（主机盲寻呼会关掉页扫描）。

## 18. 磁吸键盘

- Nanosic 803 单片机（`XM2022-152-0721B`），高通串行引擎 2 的芯片间总线，地址 `0x4c`，中断、唤醒、电源、复位、睡眠分别是 83、46、127、141、155 号引脚。人机接口设备 `0018:15D9:00A3`。不要打开串口 2（和键盘共用引擎 2 的寄存器）。
- 安卓的参照：按住一个键时内核只上报一次按下，没有自动连发，由合成器做连发；单片机每隔一段时间发 `0x22` 保活，松手时是一个空的 `0x05`。
- 难点是鬼键：Linux 在 `0x22` 保活中断排空时会再读到一个残留的空 `0x05`，像一次假抬起，合成器就停止连发。过滤逻辑放在 `nanosic-kbd-ghost.h`，主机上有单元测试 `tests/test_nanosic_kbd_ghost.py`。几次迭代：
  - `#335`：同一中断里见过厂商数据、或厂商数据后 400 毫秒内的空报告不注入。
  - `07196f2`：只在有证据（厂商数据、引脚未决、抖动、过期序号）时才丢空报告，替换掉会吞快速连打的 80 毫秒去抖。
  - `32a52b6`：Ctrl+C 之后只剩修饰键时补发抬起。
  - `dbb13e5`：中断线已经回高时，序号加一的空报告是真抬起。
  - `f541909`：Fn 音量键的消费者报告全 0 被当成鬼键，合成器把音量一直加到顶；改成 Fn 之后释放。
- udev 规则给它补 `ID_BUS=i2c`（合成器的连发需要真实总线类型），并忽略唤醒脚那个伪键盘节点（`b5c85cb`：唤醒脉冲当成重复键，抢走了正在按住的键的连发）。
- 不要用 keyd 独占这个设备：它独占后经虚拟输入设备重发的事件没有扫描码，Wayland 第一下不连发（`12cd094`）。点 Shift 切 fcitx5 用 `userspace/dagu-fcitx5-shift-tap.c`，只监听不独占。
- mutter 50.1 任意一个键松开都会取消连发（GNOME 上游问题 4675），打补丁改成只有正在连发的那个键松开才取消（`patches/mutter-50-repeat-on-other-key-release.patch`），`dagu-mutter-repeat-keep.service` 防止升级把原版库装回来。

### 20.1 硬件和点亮

链路：

```text
相机控制接口（芯片间总线）配置传感器
  → 相机串行接口物理层 → 相机串行接口解码器
  → 图像前端：相机接口 → 相机逻辑核（各处理块）→ 总线写通道 → 内存
```

两个摄像头最后都用解码器 1 + 图像前端 1，图像前端 0 空着，和安卓一致。

后摄 s5kjn1（丘钛模组）：

- 相机控制接口 0，地址 `0x10`，物理层 1，四线差分物理层。4080×3060，绿蓝红绿排列 10 位。
- 寄存器表 `overlays/linux/drivers/media/i2c/s5kjn1-dagu-regs.h`，来自安卓的传感器模块文件。模组里的单片机在醒来前不应答，开流时照写，并按 10/20/50/100 毫秒探测。
- 安卓预览是差分物理层，`0x0114=0x0300`，物理层建立时间 `0x13`。高通框架表里那份三相物理层配置（`0x0301`）会让解码器和图像前端黑屏。
- 上电顺序：接口电压 → 模拟 → 数字 → 主时钟 → 解除关断。
- 踩过的坑：硬件配置检查写死了差分物理层，设备树一改三相就探测失败；默认曝光 3840 大于帧长减余量，控件初始化报范围错；`0x0bcc` 不应答，从初始化表删掉；先上电再开物理层，会在相机时钟控制器的电源域起来前把主时钟卡死；没有 2040 宽的模式，模拟半裁仍然出约 4080，解码器溢出。

前摄 IMX596：

- 驱动 `overlays/linux/drivers/media/i2c/imx596-dagu.c`。相机控制接口 1，高通设备树写 `0x1a`，实际芯片在 `0x10` 应答，芯片号 `0x0596`。
- 物理层 4，四线差分物理层，`0x0114=3` 要在组保持释放后再写一次；建立时间按公式算，不要抄后摄的 `0x13`。
- 2592×1952，`link-frequencies = 678400000`。
- 模拟增益是索尼公式 `增益 = 1024 / (1024 − 码值)`。原来上限 `0x7f` 只有 1.14 倍，`1a0d1ac` 放到 `0x03C0`（16 倍）。

存储标定的芯片（`gt24p64e`、`gt24p128e`）和后摄对焦马达 GT9764 都还没用上。

后端：原始旁路出口一开始就能写内存（系统内存管理单元、相机片上网络都通），测试图样发生器也出过完整一帧。设备树删掉了相机的 `interconnects`，原始旁路照样能写，说明“没有带宽投票就进不了片上网络”不成立。

### 20.2 原始旁路 + 软件去马赛克时代（直到 `#629`）

```text
传感器 10 位原始数据 → 原始旁路出口 → libcamera 软件去马赛克（后 4×4 跳采 → 1020×764，前 2×2 → 1296×976）
  → 生产者转打包 4:2:2，中间裁 1280×720 → v4l2loopback /dev/video20（前）/ video21（后）→ 应用
```

为什么要回环设备：Snapshot、Chromium、腾讯会议、微信都只认普通的 Linux 视频采集节点，不会直接用 libcamera。回环设备把一切统一成“一个能打开的摄像头”。

libcamera 侧（`linux-mainline/libcamera/`）：

- 取景和录像默认跳采（宽 ≥3000 取 1/4，≥2000 取 1/2）。处理后的最大尺寸必须卡在跳采尺寸，否则 PipeWire 要 1920×1080 时会 1×1 全采、Snapshot 卡死。
- 线程固定 2 个、绑 0–3 号核，否则 8 线程会饿死合成器和触控。
- WirePlumber 关掉 libcamera 监视器：Chromium 经它打开时，1200 万像素软件去马赛克跑在会话核上，桌面掉帧。

和应用兼容的坑（大部分在回环驱动 `overlays/linux/drivers/media/v4l2loopback-dagu/` 和 `camera-loopback/` 里）：

| 问题 | 修法 |
|---|---|
| Chromium 不列同时声明采集和输出的节点 | `exclusive_caps=1,1`；守护进程开机就把格式盖成打包 4:2:2 1280×720，客户端还没开流时也能看到采集能力 |
| 节点号撞上视频编解码 | 回环用 20、21，避开 14、15 |
| 腾讯会议切前后摄像头崩溃 | 会议库只申请 4 个缓冲、只映射这 4 个；`max_buffers=8` 时出队了 4–7 号，读到野地址。改成 4（`ecdcb59`） |
| 会议库的格式约定 | 必须是打包 4:2:2 四字码；查询到的图像大小是宽×高×2；映射长度要多带一段 4:2:0 色度填充；写成宽×高×4 会把它的转换函数打崩 |
| 关掉格式盖章的输出句柄后桌面相机冻在灰帧 | 守护进程一直持有输出句柄，子进程通过 `DAGU_LOOP_FD` 继承，不再二次打开（`f767881`） |
| PipeWire 给回环设备带上共享缓冲修饰符 | `spa-v4l2-dagu/no-loopback-modifier.patch` 去掉 |
| PipeWire 缓存了盖章之前的能力，Snapshot 说没有摄像头 | `dagu-camera-pw-kick.sh` 在缺源时重启 WirePlumber |
| 上次强杀后媒体链路还开着，再开报忙 | `dagu-camss-graph-reset.sh` 在 PipeWire、WirePlumber 启动前复位媒体图 |
| 画面发白、颗粒、镜像不对 | 软件去马赛克本来就做了伽马，再加一次 sRGB 和 4 倍前置增益会削顶；传感器在玻璃后面装反 180°，水平垂直都翻是镜像，只翻垂直才能让手写字正着读（`eda87dd`） |

验收：`camera-loopback/tests/test_app_v4l2.c` 模拟会议软件、Chromium、PipeWire 的打开顺序，包括热切换、同时打开、写入方交接、防闪烁。

这条路能用，但它是洞：处理器在解拜耳，预览开着时桌面和触控都会受影响。所以一直把“图像前端出线性 4:2:0 半平面图像”定为终点。

### 20.3 安卓在跑什么

HyperOS 板上的后摄预览（`b81450d`、`dagu-camss-pix-audit.md`）走的是图像前端 1 像素通路：写通道 4/5 输出 1920×1080 的高通压缩格式（打包器 `0xB`），同时写通道 6/7 输出给图像处理引擎的四倍缩小图，`CORE_CFG_0=0x60000800`，解码器像素口 `cfg0=0x802b20e3`。安卓的 `/dev/mem` 有严格限制，所以相机逻辑核的值最初靠静态分析 `camera.qcom.so` 的命令打包函数，以及转储得来。

Linux 的产品约定和安卓不同：线性 4:2:0 半平面，亮度打包器 3、色度打包器 1，不用高通压缩，不用图像处理引擎。

### 20.4 后摄像素通路：`#308`–`#365`

测试：`scripts/dagu-ife-pix-test.sh`（图像前端 1、后摄、1920×1080、开流 12 秒）。门：至少 3 帧非零、`r0114=0x300`、串口小工具活过 30 秒、只刷 B 槽。

开头的失败签名（`#333`）：相机接口计数满（`pix=4080 line=1530`，每时钟 2 像素所以行数减半），然后像素管线溢出；写通道打包器状态从来没收到有效数据，地址状态锁了却没消耗，相机片上网络写出 0 次，文件 0 字节。传感器和相机接口在跑，相机逻辑核到打包器这一段一个字节都没交出来。

方法：每一刀只改一类寄存器，而且必须在高通相机用户态框架的命令打包函数里找到出处（立即数地址和字段宽度）。判刑标准：

| 现象 | 判定 |
|---|---|
| `line=0` | 空使能砖墙（某块打开了但查找表是空的），立刻撤回 |
| `STREAMON` 报 `EPIPE` | 编程了没有程序的缩小出口，撤回 |
| 读回被截断或弹成 0/1 | 这个寄存器不是以为的那个窗口 |
| `line=1530`、地址没消耗、值粘住 | 这一项不是卡死点 |

一路排除过的（摘要，完整表在 `dagu-ife-pix-nv12-attempts.md`）：

- 空使能就是砖墙的块：坏点校正、线性化、高动态、全局色调（空）。
- `CORE_CFG_0` 跟安卓 / 关掉双输出：都不行。不能把拜耳顺序塞进 `CORE_CFG_0`（那是数字信号处理器直通模式）。
- 往缩小出口塞裁剪（那其实是查找表配置）；空的 `0x5e00` → `EPIPE`。
- 一长串“粘住但没用”：解复用、去马赛克、白平衡、镜头阴影网格、色彩校正、色彩空间变换、裁剪、圆整钳位、缩放尺寸、黑电平、降噪。
- 读回 0 不一定没写上：有些寄存器只写不读。
- 调试状态字 `clcstat` 和 `TOP_DEBUG_CFG=1` 是盲的，不能拿来定位。
- `COMP_CFG` 读回 0 是对的，只有双图像前端才写。

转折：

- 用 Magisk 在相机进程里转储到 1 MiB 的活命令缓冲，发现显示满幅走的是完整打包而不是精简打包。
- `#349`：照活缓冲写裁剪和缩放（`0xfef0bf3` / `0xc043dbcf`）加圆整钳位，第一次出队 3 帧，但全是 0。
- `#350`：撤回圆整钳位又回到 0 字节，说明 Linux 自己理解的“全保留”写法是误读（高低半字顺序反了）。
- `#351`–`#359`：逐块关掉，写出照常但仍全 0。
- `#360`：关掉坏点校正 30（`0x2e58={0,0,0}`）后第一次出真实画面（室内的罐子）。零查找表 + 使能 = 把整幅乘成 0。过门。
- `#361`：加回去马赛克，整幅偏绿（色度均值约 21）。`#362`：色彩校正不是绿源。`#363`：色度圆整 7→6，证伪“打包器取低位”。`#364`：色彩空间偏移写进低 10 位会把矩阵乘成 0。
- `#365`：偏移写 `0x02000000`、色度打包器改 1（8 位平面），色度均值 132.8，过了原点。
- 合入 `8db99b7`（2026-09-17）。

### 20.5 前摄像素通路：`#367`–`#624`

前摄用同一条图（物理层 4 → 解码器 1 像素口 → 图像前端 1），但几何和拜耳顺序不同（解复用奇偶 `0xca/0x9c`，不能抄后摄的 `0xac`）。这一段的坑最多：

- `#373`：溢出第一次有了名字，违例号 19 = 色度缩放器。之后几刀改色度裁剪和缩放的尺寸、相位都还是 19。
- `#381`：裁剪改成活流的 `0x0a1f05bf` 加相位，违例号回到 0。
- `#382`：中间和后级钳位改成 2304 宽，第一次出非零图像（差 2048 字节一整帧）。
- `#386`：钳位和写通道一起改成 2320×1320，得到 4591616 字节，离整帧差 1984 字节。
- `#394`：关掉解码器的溢出恢复（`ERR_RECOVERY_CFG0=0`），溢出消失，看到第二个帧起始（`24c8255`）。恢复机制多发的那几行才是溢出源。
- 差的 1984 字节：试了十几种写通道和缩放的改法都不对。最后从地址算出来：色度最后一行从 `0xff460eb0` 开始，写了 336 字节正好停在 4 KiB 边界 `0xff461000`。`#501` 把行步长改成 4096，第一次得到一整帧 8110080 字节。后摄 1920 也跨 4 KiB 却能写满，所以不是通用的总线截断；不要用“帧增量向上对齐”掩盖。
- 安卓第一张表（`#412`–`#462`）：重放活缓冲里的第一张表，里面叠着全幅、640 的人脸检测裁剪、缩小出口、统计，每一刀都是 0 字节，整体放弃。
- 之后一直卡在“只出一帧”：第二个帧起始后不到 1 毫秒管线就停，没有任何错误中断。`#502`–`#507`、`#612`–`#624` 试了注册更新时机、重装写通道、丢帧图案、照抄安卓缩小通路、重放安卓命令包、伽马和白平衡表、帧尺寸和相位，全都还是一帧。

### 20.6 安卓活流转储的方法

细账：`dagu-ife-android-dump-reverse.md`。

- 命令格式按高通开源的 `cam_cdm_util.h` 解析：`0x3` 连续写、`0x4` 随机写（活流的写通道配置在这里，早期分析器只解析 `0x3`，所以一度以为安卓没有显示满幅写通道）、`0x5` 间接、`0x8` 换基址。
- 写通道 n 的地址是 `0xaa00 + 0x200 + n × 0x100`，图像配置 0 是 `(高 << 16) | 宽`。
- `camera.qcom.so` 静态分析：裁剪和缩放 9 字连续写的来源偏移，显示满幅时缩放写到 `0x4c60/0x4e60`，人脸检测时写到 `0x6460/0x6660`。
- 高通相机用户态框架的详细日志：`/data/vendor/camera/camxoverridesettings.txt`（用完恢复）。
- 只读内核模块：手写汇编，对齐原厂内核的版本魔数和映射属性，`dagu_ife_rd`、`dagu_ife_top`（96 次采样调试字）、`dagu_ife_full`（`0x0`–`0xd000` 全窗）。脚本只在相机进程有 20 个以上共享缓冲、而且图像前端中断 1 秒内在涨时才加载，因为空闲时图像前端时钟关着，读一下就挂总线。
- 全窗对比：Linux 和安卓有 440 个字不同。

### 20.7 前摄只出一帧的根因：人脸检测支路（`#625`、`#626`）

细账：`dagu-front-ife-fd-branch-fix.md`。

换方法，先找“谁停了”：

- 高通内核头文件 `cam_vfe480.h` 定义了 14 个顶层调试字（`0x80`–`0x8c`、`0x9c`–`0xc0`，`0xdc=1` 打开）。每个字 8 个 4 位字段，一个字段对应一个相机逻辑核模块。驱动以前只在溢出时读前 4 个，这次没有溢出，所以没人看过。
- 位义从第一帧的变化轨迹反推出来：位 0 就绪、位 1 有效、位 2 空闲。`5` 是空闲且就绪，`1/3` 是帧内流动，`2` 是“手里有数据交不出去”。
- 第一次用用户态 `/dev/mem` 采样：停机时 `0xa0`–`0xac` 有 16 个位置是 2，下游全是 1；安卓采 96 次全是 5。用户态轮询在后摄测试关时钟后还在读，把 Linux 板总线挂死重启了一次，所以第二步把采样搬进驱动。
- `#625` 一次刷机装好仪器：飞行记录器（高精度定时器从相机接口启动开始读 23 个字，只记变化，在关时钟前停）和运行时覆盖表（`dagu_ovr`，时机 `init/go/sof/eof`，只允许写 `0x2c` 和 `0x2000`–`0x9ffc`）。之后每个假设是一次 15 秒的实验。

记录器看到：帧间隔里 `0xa0` 是 `0x55515155`（安卓是 `0x55555555`），第 2、4 个字段一直“就绪但没空闲”，它们没能结束第一帧。逐项关块，只有关掉 `0x4400/0x4600` 或 `0x4800/0x4a00` 才能出 3 帧，四个全关连续 90 帧。

根因：驱动把这四块当成显示通路的“裁剪”和“中间钳位”，实际上它们是人脸检测支路（缩放 + 圆整钳位，输出到写通道 8/9）。依据：高通的输出口表里人脸检测对应写通道 8/9；安卓读回能对上 640×480（`0x446c=0xc081999a` 是 2592/640 的定点数，`0x4474=0xc0822222` 是 1952/480）。Linux 打开了这条支路、填的是显示尺寸、写通道 8/9 却关着，于是第一帧收不了尾，第二帧数据进来时堵住共用的上游，整条管线连同相机接口一起停下，不报任何错。

修复 `#626`（`c8cd60b`）：新增 `vfe_480_fd_off()` 把四块关掉，删掉所有往这四块写值的代码；`apply-overlays.sh` 里 18 条要求保留旧裁剪写法的检查换成一条“人脸检测支路必须关着”。回归：前摄 3 帧、90 帧都过；后摄 3 帧照常。

### 20.8 确定性的显示通路程序和测试图法（`#627`–`#629`）

细账：`dagu-ife-disp-pipeline.md`。

修完停机以后，画面还是左上角 1:1 裁出来的、颜色不对。两件事一起做：

- 驱动新增 `vfe_480_disp_program()`（`980f786`）：每次开流按传感器和输出格式重写整条显示通路，通路外的块全关。旧的有状态写法会把上一路流的寄存器漏到下一路，造成新的停机和违例，保留在 `dagu_disp_new=0` 后面。
- 增加调试接口 `/sys/kernel/debug/dagu_ife1/{prog_front,prog_rear,live,dmird}`：开流时加载程序，`@sof` 开头的行每帧执行，`live` 下一帧执行一次。

寄存器含义用传感器测试图测出来，不靠猜：

- 通过相机控制接口直接写传感器的 `0x0600`（彩条 2，纯色 1，纯色电平 `0x0602`–`0x0608`）。驱动里测试图控件那条路在 IMX596 上不生效。
- 改一个寄存器，量一次输出的亮度和色度，对着 BT.601（Broadcasting Television Recommendation 601，国际电联标清视频色彩标准）彩条的理论值解方程。
- 测出来的结论（详表在专题文档）：去马赛克白平衡增益的通道顺序、色彩校正矩阵按输入通道绿蓝红排行和定点 7、伽马表按 8 位输出单位存、色彩空间变换的亮度和色差系数定点、缩放器 `+0x64` 必须写 `0x600`、色度相位是亮度的两倍、查找表写入口的三个寄存器。
- 前摄在图像前端里必须按红绿绿蓝排列，虽然传感器报的是蓝绿绿红（驱动里用 `dagu_pattern_override` 覆盖，没改传感器上报的格式码）。
- 黑电平：不开 `0x3400` 块（黑电平 + 拜耳降噪）时，传感器黑（码值 64）落在约 70，整幅发灰；打开后约 9。

验证：前后两个摄像头都输出标准彩条（白 255、黄 226、青 179、绿 150、品红 105、红 76、蓝 29、黑 0）；纯色电平扫描与理论值相差 1–4 个码值。

我们没有用网上泄漏的高通相机用户态框架源码，所有寄存器含义都是黑盒测出来的。

### 20.9 生产者和自动曝光、自动白平衡（`8a82c08`）

`camera-loopback/cpp/dagu_hw.cpp`：

- 媒体图：复位链接，接物理层到 `msm_csid1:0`、`msm_csid1:4 → msm_vfe1_pix:0`，像素口输出 1280×960。选传感器原始比例（4:3）是为了让镜头阴影网格按全幅对齐；在相机接口裁成 16:9 会让网格错位。
- 输出：线性 4:2:0 半平面 1280×960，生产者取中间 16:9 一带打包成 1280×720 的打包 4:2:2，前摄只垂直翻、后摄只水平翻（保持原来的方向）。单核约 23%。
- 画质程序：通用饱和度恢复矩阵（每行和为 1，没用色卡标定）；色彩空间变换用有限范围（摄像头约定）；色调曲线是 sRGB（standard Red Green Blue，标准红绿蓝色彩空间）加轻微黑位裁切和 S 形；前摄镜头阴影校正只用亮度部分（数据取自这台平板 HyperOS 里抓到的 17×13 网格），红蓝两半在这个视角下会让四角偏品红、中心偏绿。
- 自动曝光：中心加权，目标亮度 110（高光多时 95），对数域阻尼加死区；先加曝光时间，超过 10 毫秒按 10 毫秒取整避开 50 赫兹灯光；再加模拟增益（前摄连续，后摄只能整数倍）；最后用图像前端数字增益补，最多 4 倍。
- 自动白平衡：线性化后的灰世界，剔除饱和、过暗和高饱和像素，每次走 25%，增益限 1.0–3.2。
- 起不来就退回软件去马赛克；`DAGU_CAMERA_SOFTISP=1` 强制退回。

结果（`#629`，重启后复测）：两个摄像头各连续 150 帧约 5 秒取完（每秒 30 帧）；`test_app_v4l2` 全部通过（Snapshot、PipeWire、会议软件格式、热切换、同时打开、防闪烁）；日志里全是硬件通路，没有一次退回；3A（Auto Exposure / White Balance / Focus，自动曝光 / 白平衡 / 对焦）统计前摄曝光 30 毫秒、模拟增益 16、白平衡红约 2.3、蓝约 1.44，画面肤色和墙面颜色自然。

## 21. 根文件系统、桌面和应用

### 21.1 根文件系统

- Ubuntu 26.04（resolute），选它是为了 Mesa 26.0.8 和 mutter 50 的补丁能对上。`build-rootfs-desktop.sh` 的流程：下载 Ubuntu 基础包（或 `debootstrap`）→ 在 qemu 用户态里 chroot 跑 `rootfs-desktop-setup.sh`（装包、编译产品程序、写配置和服务）→ 清掉构建机的密钥和机器号 → 打成 8 GiB 无空洞的 ext4（无空洞是为了稀疏刷写不跳过日志区）→ zstd 压缩并生成校验和。

## 24. 心得

### 24.1 先找“谁停了”，再找“哪个值不对”

前摄只出一帧这件事，从 `#412` 到 `#624` 刷了两百多个内核，每次都是“猜某个寄存器值不对，改一个，刷机，看结果”。真正解决它的是 `#625` 那一次刷机：把顶层调试字的采样放进驱动，再加一个运行时覆盖表。之后每个假设是一次 15 秒的实验，一个下午就定位到人脸检测支路。

同样的模式在别处也出现过：

- 桌面卡顿：先用事件跟踪证明“垂直同步照走、只是没提交”，再证明“内核栅栏没卡”，范围才缩到合成器和浏览器之间。如果一开始就去改显示驱动的等待超时，会改错层（那个补丁后来确实被否决了）。
- 启动：没有控制台时，“几秒回兔子”本身就是信号。3–6 秒、20–25 秒、40 秒以上分别对应完全不同的死法。

经验：遇到“没有任何报错就停了”的问题，第一件事不是猜值，而是找能看到每一级状态的观测点，把实验成本从“一次刷机”降到“一次运行”。

### 24.2 先把实验变便宜

这个项目里最有回报的投入都是工具：

- `fb-usb.py`：解决了刷机本身不可靠的问题。之前很多“秒回”其实是镜像根本没写进去。
- 刷机时序表：不需要串口就能区分引导程序拒收、内核入口崩溃、看门狗、小工具没起。
- 相机飞行记录器、覆盖表、调试接口：一次刷机换来几百次不刷机的实验。
- `dagu-dpu-jank-capture.py`、`dagu-dpu-hole-blame.py`：把“感觉卡”变成“第 99 百分位多少毫秒、超过 50 毫秒的洞几个、洞里谁在睡”。
- 安卓只读采样模块：在不碰 HyperOS 板的前提下拿到真实硬件状态。

### 24.3 用已知输入测黑盒，而不是抄数值

后摄过门时，靠的是逐个照抄安卓活缓冲里的值，再逐块关掉看效果。能出图，但不知道每个值的含义，前摄换个几何就全不对。

最后定下颜色流水线，靠的是传感器测试图：输入是已知的彩条和纯色电平，改一个寄存器、量一次输出，对着标准彩条解方程。半天就把白平衡、色彩矩阵、伽马、色彩空间变换、缩放器的格式和定点位数全部测清楚，而且前后两个摄像头一次对上。

经验：照抄能让东西先动起来，但要让它“对”，得能解释每个值。已知输入加可测输出，是理解黑盒最快的办法。

### 24.4 对照，但不要照抄

HyperOS 板是最好的参照，但很多地方 Linux 的约定和安卓不同：

- 安卓相机输出高通压缩格式给图像处理引擎，Linux 要线性格式给应用。所以写通道、打包器、缩小出口都不能照抄。“对齐硅和几何，不是包装。”
- 安卓的第一张命令表里叠着人脸检测和统计，整张重放反而 0 字节。
- 安卓的音频增益是按开着回声消除设的，Linux 关着时要另算。
- 原厂充电策略“电流不够就加电压”依赖完整的状态反馈和中断，我们只移植了一部分，照抄就把电压一路加到 10.5 V。

### 24.5 同一个名字、同一个地址，不等于同一个东西

- `0x4400/0x4800` 在驱动里叫“裁剪”和“中间钳位”，实际是人脸检测支路。
- `vblank timeout: 400000` 的第 22 位在源码里有两个名字，一个是压缩刷新位，一个是这颗芯片根本没有的光标图层。
- 高通相机用户态框架里打包器 3 对应的是压缩格式的 10 位打包，不是线性。
- 高通设备树里写前摄地址 `0x1a`，芯片实际在 `0x10`。
- 读回 0 可能是只写寄存器；调试状态字在某些选择下是盲的。

经验：模块名、位义要从输出口表、硬件读回或者已知输入实验里核实，不能从变量名推断。

### 24.6 根因修复的规矩

仓库规则 `dagu-root-cause-fix`：动手之前先回答三件事，看到了什么、为什么会这样、什么能证明根因没了。下面这些不算修复：加超时、重试、睡眠、预加载库、屏蔽中断、关节点、把工作推回处理器、界面上显示成功。

项目里真正被这条规矩救过的例子：

- 扬声器小声：可以加软件音量“补响”，但根因是位宽，修了以后不需要任何补偿。
- 前摄一帧：可以在中断里强行重启管线，但根因是一条没有接收者的支路。
- 关机充电和桌面冲突：可以在桌面服务里加延时，但根因是 systemd 的冲突语义会丢任务。
- 桌面卡顿：可以加一个每 8 毫秒重画的“泵”，实际试过，一部分场景变好、另一部分更差；真正的根因是一个实验特性把窗口算成被遮挡。

### 24.7 把规矩写进机器

文档会被忘掉，脚本不会：

- `apply-overlays.sh` 的内容守卫：关键修复被删掉，编译前就拦下。
- `build-kernel.sh` 的断言：危险配置（片上互连、10 位、函数跟踪、入口探针）一出现就退出。
- 单元测试锁住踩过的回归：麦克风、键盘鬼键、关机充电判断、播放顺序、毛玻璃尺寸规则。
- 回环设备的测试程序模拟真实客户端的调用顺序，每次改相机都跑。

### 24.8 平台层的教训

- 固件环境划定了边界。高通虚拟机监控程序下，片上互连、串行引擎包装层、通用直接内存访问、某些电源轨都碰不得。与其每个外设各绕各的，不如找出统一模式（单引擎固件装载、删互连属性、关键驱动内建），所有外设套用。
- 模块在根文件系统挂上之前没用。启动路径上的东西一律内建。
- 数据线串口是最好的日志通道，但它本身也会被抢（网卡小工具、主机模式）。
- “看起来像砖”不一定是砖。7 月那次闪存里什么都没写坏，是内存里的挂死加上紧急下载模式的授权门槛。先强制关机，再考虑救砖。

### 24.9 用户态的教训

- 很多“花屏”“没声”“没摄像头”是两端对格式的约定不一致：窗口修饰符、写通道打包器、回环设备的映射长度、用例管理器的控件名。先把两端各自认为的格式打出来对一遍。
- 两个进程互相等待时，单看任何一边都像“正常在等”。合成器在等损坏区域，浏览器在等帧回调，图形处理器空闲。要同时看两边和内核。
- systemd 的依赖会有副作用：冲突关系会丢掉别的服务的启动任务；启动失败太快会被限频，整个会话都起不来。
- 预加载库适合做实验，不适合当产品。这个项目里写过几十个预加载实验库，最后上产品的只有极少数，而且都被替换成了源码补丁或者撤掉了。
- 应用兼容要照真实客户端的调用顺序测。会议软件只映射 4 个缓冲、映射长度要带色度填充，这类约定文档里不会写，只能在测试程序里复现。

### 24.10 过程纪律

- 两块板、两个序列号，刷之前核对。HyperOS 板永远只读。
- 只刷 B 槽，A 槽留救援。不刷 `xbl`、`abl`、`super`，不上锁。
- 一次刷机只改一个变量，内核编号贯穿遥测目录（`out/camera/ife-pix-<编号>/`），文档里的每一刀都能找回数据。
- 文档只写做过、有遥测的结论，包括证伪的。证伪清单（“禁止再做”）和结论一样重要，它防止几周后又绕回同一条死路。
- 总表会过时。专题做完要回头更新总表，否则后来的人会按旧状态做判断。本文第 2 节就列出了 9 月总表的过时项。
- 不把无线网络名、密码、网卡地址、密钥放进仓库或公开镜像。

### 24.11 走过的弯路

- ARM 版 Windows 路线花了约三周，卡在一个没有任何可观测性的大容量存储链上，最后进了紧急下载模式。回头看，应该先选可观测性最好的路线。主线 Linux 有串口小工具、有事件跟踪、有源码，能看见自己在哪。
- 前摄在“猜值”上花了两百多次刷机。如果在第一次出现“无报错停机”时就装上调试字采样，能省下大半。
- 桌面卡顿试了七个 mutter 变体和一堆预加载钩子，真正的根因是一个实验特性。先做定性（内核没问题、是用户态没提交），再看配置层面有没有明显异常，可以更早找到。
- 67 瓦先照抄原厂“加电压”逻辑，结果把电荷泵推进故障。原厂策略依赖的中断和反馈我们还没有，应该先锁死安全的电压，再一项项加回去。
